Abstract

This paper proposes several mechanisms to enable relocation (possibly not trivial) of automatic variables in C++. We cover several topics, such as trivial relocatibility, container optimizations, supports for relocate-only types, library changes and the impact of the existing code base.

1. Overview

Move semantics were introduced with C++11, and have improved the language in many aspects. However they have also brought their lot of defects:

  • std::move does not move ;

  • moved-from objects are in an unspecified state, and more often than not, must not be reused ;

  • constant objects cannot be moved ;

  • classes that want to support move-semantics must either have a natural empty state (like strings, containers or smart pointers) or force one into their design, usually creating a loophole in their class invariant.

C++26 further introduced trivial relocatability, as an incomplete solution to all those issues (only trivial relocation, and only for objects that live in dynamic storage).

We propose to resolve all these issues by bringing support for relocation, not only trivial relocation, to all objects. In particular to objects with an automatic lifetime.

We define relocation as the operation of constructing a new target object while simultaneously destructing the source object. Relocation will happen thanks to a new keyword reloc and a new relocation constructor (with signature T(T reloc)).

// with: void foo(non_null<unique_ptr<T>>)

non_null<unique_ptr<T>> const ptr{new T};
ptr->do_stuff();
foo(reloc ptr);
// ptr cannot be reused or else the program is ill-formed

This tackles every flaw not solved by move-semantics:

  • reloc does perform the relocation ;

  • relocated objects cannot be re-used, or else the program is ill-formed ;

  • relocation disregards cv-qualifiers, so constant objects can be relocated ;

  • classes that want to support relocation can do so without breaking their class invariant, as the relocated-from object is simultaneously destructed.

Another major addition of this proposal is the object decomposition feature. Object decomposition enables to relocate data members of compound types (such as std::pair) and to easily write used-defined relocation constructors and relocation assignment operators.

pair<std::string const, int> const keyValue reloc = extractKV();
storeKey(reloc keyValue.first);

template <class First, class Second>
class MyPair
{
public:
    First first;
    Second second;

    // user-defined relocation constructor (could have been defaulted)
    MyPair(MyPair rhs reloc) : first{reloc rhs.first}, second{reloc rhs.second} {}
};

The reloc keyword in the object definition indicates that the object is decomposed, which allows the relocation of its subobjects with reloc.

This proposal introduces:

  • two new special member functions: a relocation constructor T(T reloc) and a relocation assignment operator T& operator=(T) or T& operator=(T reloc) ;

  • a new keyword: reloc which backs a new operator and the object decomposition feature ;

  • slight changes to overload resolution rules ;

  • might introduce ABI breaks to some functions (opt-in).

This proposal does not introduce a new value category: instead it completes C++ tripartite value system as we propose relocation to happen from prvalues.

1.1.1.2. Generalization of object decomposition

One of the major changes we introduced is the generalization of the decomposition feature, which was introduced by the "decomposing functions". The reloc keyword can now be used to decompose any object, not only the this parameter of a member function. This has several advantages:

  • it greatly simplifies the writing and the understanding of the relocation constructor and reloc assignment operator ;

  • it simplifies the handling of relocate-only subobjects in user code ;

  • it removes the decomposing functions feature as they are being replaced by a more generic object decomposition feature ;

  • the whole proposal is more unified as all those changes are now built on top of the object decomposition feature.

In R4, we take a slightly less conservative approach: any function that takes a parameter by value, whose type provides a relocation constructor but no move constructor, must have control over the lifetime of that parameter.

Discussion about this change is detailed in the reloc with function parameters section.

2. Motivation

2.1. Relocation of automatic variables allows for safer code

2.1.1. Support for always-valid types

Tony Hoare stated that the introduction of the null reference was his "billion dollar mistake". Null pointers are a common source of software failures, often causing software crashes and interruption of services.

We all know that when using a pointer, we need to ensure of its validity first. Unfortunately, most of C++ classes suffer from the same design flaw. Because of move-semantics, when an object has been moved, it is in a valid but unknown state. If a moved-from object is to be reused, the object must first be reassigned to some known state before doing anything else with it. This approach is so error-prone, that many guidelines advise to simply drop the moved-from object.

Because of this, in C++ it is not possible to write a class that provides a very basic guarantee: a pointer that is always valid. It is not entirely true as we do have gsl::non_null<std::unique_ptr>, but as this class provides no move constructor and no copy constructor, its usefulness is greatly diminished. It can only be used as an immovable stack variable, or stored in a node-based container.

Move-semantics requires the moved-from object to be still valid. This greatly complicates some class design. Hence our always-valid pointer class can hardly have a move constructor: an efficient move constructor would set the address of the moved-from object to nullptr, but the class invariant forbids this value. (An inefficient move constructor would perform an extra memory allocation, and would leave the moved-from object with a valid pointer, but pointing to a moved-from object... But no one wants to pay the cost of an extra memory allocation for an object that will be dropped right away.)

This can be extended to any class which aims to provide always-valid access to some resource. None of those can be correctly implemented today in C++ with move semantics, unless everyone complies with the status-quo rule that a moved-from object must not be reused. Relocation fixes the problem completely. As relocation moves and destroys in the same operation, the relocated-from object ceases to exist and cannot be reused. No invalid state must be forced into its class design, which would break its class invariants.

For instance, an always-valid pointer class can be:

template <class T>
class box
{
public:
    template <class... Args>
    explicit box(Args&&... args) : _ptr{new T{std::forward<Args>(args)...}} {}
    ~box() { delete _ptr; }

    box(box const&) = delete;
    box(box&&) = delete;
    box(box reloc) = default;

    box& operator=(box const&) = delete;
    box& operator=(box&&) = delete;
    box& operator=(box reloc) = default;

    T* operator->() const { return _ptr; }
    T& operator*() const { return *_ptr; }

    // exchange this with a new box, return its former value
    box exchange(box = {}) noexcept;

private:
    T* _ptr;
};

This class achieves its purpose in very few lines. It is not part of this proposal (an STL version would likely feature support for custom allocators and custom destructors). However we believe that relocation is a major prerequisite for such classes. Such box classes and the likes landing someday in C++ is a strong motivation for this proposal.

2.1.1.1. The design loophole of std::indirect and std::polymorphic

std::indirect and std::polymorphic both got adopted into C++26. However both classes suffer from a serious design flow: they attempted to be always-valid classes yet have a move constructor.

One cannot construct an empty std::indirect (or std::polymorphic) object, but yet it can become valueless after a move operation, and the valueless_after_move() member function can be used to verify its state.

Both classes would have greatly benefited from a deleted move constructor and a defaulted relocation constructor. This way, both classes would indeed have been always-valid, and no member function would have been needed to check that aberrant state.

C++26 STL hardening may mitigate this, but it will always be an inferior solution compared to what we propose: a solution at type system level which will be statically checked.

2.1.2. Simplify class writing

Currently in C++, if you write a struct which uniquely owns a resource, you have to write a lot of boilerplates:

struct A {
    A(A &&src) : ptr(src.ptr) {
        src.ptr = nullptr;
    }
    A(const A &) = delete;
    A &operator=(A &&src) {
        if (&src != this)
        {
            delete ptr;
            ptr = src.ptr;
            src.ptr = nullptr;
        }
        return *this;
    }
    A &operator=(const A &) = delete;
    ~A() {
        delete ptr;
    }

private:
    T *ptr;
};

And this is just one data member, the required amount of duplicated efforts are correlated by the count of uniquely-owned resources in the wrapper type. Requiring the users to manually write all the assignments and then setting the source object back to null state can be tiresome and bug-prone. All the efforts went in, just to satisfy a niche scenario (use after move).

Also note the address check in the move assignment operator. In our experience, this check is often forgotten in user code, leaving the door open for potential vulnerabilities. This check must always be done, also to satisfy another niche scenario (a = std::move(b), in the unlikely event where one is a reference on the other).

With relocation constructors, this is greatly simplified, because now there’s less situations (moved-from state) to worry about:

struct A {
    A(A reloc) = default;
    A(const A &) = delete;
    A(A &&) = delete;
    A& operator=(A rhs reloc) {
        delete ptr;
        ptr = rhs.ptr;
        return *this;
    }
    A &operator=(const A &) = delete;
    A &operator=(A &&) = delete;
    ~A() {
        delete ptr;
    }

private:
    T *ptr;
};

In addition, the prvalue semantics further simplifies class writing: the address check in the assignment operator if (&src != this) is no longer needed. Indeed, thanks to prvalues, it is impossible for the src parameter to occupy the same address as this.

2.1.3. reloc is a safer alternative to std::move

The reloc operator is a safer alternative to std::move. The reloc operator prevents use-after-relocation errors, and allows to relocate constant objects.

reloc can be used as a drop-in replacement to std::move, with similar performance:

// with std::string a, b
foo(std::move(a));
vector.push_back(std::move(b));

// becomes:
foo(reloc a);
vector.push_back(reloc b);

There are still a couple of cases where std::move is still valuable:

  • when applied to a data member, or a non complete object. In which case, the equivalent reloc expression would be ill-formed (see relocating data members for alternatives).

  • when use after move is explicitly intended. If such expressions are promoted to reloc, then the expression that reuses the relocated objects will be ill-formed. Note that such std::move calls today would benefit of being replaced by std::exchange calls, hence no moved-from objects are handled in user code.

Note though, that a mere find and replace from std::move to reloc in a code base will create compilation errors on the above cases (no quiet code break).

2.1.4. Relocation loves constant objects

Automatic objects are recommended by various guidelines to be constant, since a constant object will not change throughout its lifetime, simplifying reasoning about program state both for humans (coders, reviewers, maintainers) and for machines (compilers, tooling). Allowing an object to be const throughout its lifetime but give up its resources at the end of its lifetime allows for better, safer code.

2.1.4.1. Constant automatic variables can be relocated

const usefulness is greatly diminished because of move-semantics, since the move constructor cannot work with a constant source object. Hence for those, the program silently falls back to calling their copy constructor...

// with: void bar(A);

A const a = someFunc();
bar(std::move(a)); // silently calls A's copy ctor, performing a deep copy...

As a direct consequence:

  • some developers will use const to naively declare constant objects as so - as one would expect from the language - while being unaware of the side-effects. This may lead to unoptimized code, with the copy constructor being called silently while std::move is explicitly called ;

  • knowledgeable developers will rather not use it if they can foresee the negative side-effect, which will improve performance at the cost of code readability.

This is a missed opportunity and it leads to poorer code. With relocation semantics, we aim to make const shine again. Constant objects can be relocated, they are just destroyed when done so.

A const a = someFunc();
bar(reloc a);

NOTE: The above snippet suffers from no pessimization even if A only has a move constructor and no relocation constructor. Indeed reloc a promotes a to a prvalue, which occupies the same storage as a, and stripped of the cv-qualifiers that previously applied to it. It will effectively call A’s move constructor, with a deconstified rvalue reference on a. This further proves that reloc is a superior alternative to std::move.

We also have to consider that the Immediately Invoked Function Expressions (IIFE) decouples the possibilities to declare constant variables (even when they have a complex initialization routine), were they not hindered down by std::move.

Consider the following code snippets, and see how const+reloc improves the code:

Before Constified + relocation (IIFE) 
void foo(A a, B b, C c);

void bar()
{
  A a = getA();

  B b = getB(a);
  b.processData();

  C c = getC(a.token(), b);
  c.fetchAll();
  c.processData();
  c.finalize();

  foo(std::move(a), std::move(b),
    std::move(c));
}

void foo(A a, B b, C c);

void bar()
{
  A const a = getA();

  B const b = std::invoke([&] {
    B b = getB(a);
    b.processData();
    return b;
  });

  C const c = std::invoke([&] {
    C c = getC(a.token(), b);
    c.fetchAll();
    c.processData();
    c.finalize();
    return c;
  });

  foo(reloc a, reloc b, reloc c);
}

NOTE: We expect the reloc operator to also multiply the possibilities to declare constant variables, with or without the IIFE idiom:

Constified + relocation (no IIFE) 
void foo(A a, B b, C c);

void bar()
{
  A const a = getA();

  B b_mut = getB(a);
  b_mut.processData();
  B const b = reloc b_mut;
  // b_mut can no longer be used

  C c_mut = getC(a.token(), b);
  c_mut.fetchAll();
  c_mut.processData();
  c_mut.finalize();
  C const c = reloc c_mut;
  // c_mut can no longer be used

  foo(reloc a, reloc b, reloc c);
}
2.1.4.2. Constant data members better expresses class invariant

In addition constant member functions and constant data members in class design enable to explicitly state class invariants. This subsection adds on the Support for the always-valid types and the Simplify class writing sections: a constant data member, due to its constant nature, cannot be set to an empty state. Hence it is intrinsically backing an always-valid state, and simplified constructor/destructor writing.

It’s not uncommon to find in production code like this:

class SomeType
{
public:
    // some parameterized constructor
    // SomeType(...)

    SomeType(SomeType&&) = default;

private:
    std::string const _key1;
    std::string const _key2;
    int _val;
};

Here the developer innocently qualified _key1 and _key2 as constant. In their mind, their value was never to change in the lifetime of the object. This being part of the class invariant, it only feels natural to enforce the class invariant in the code, with the const qualifier. However as we have seen, this will cause deep copies of the constant objects in the move constructor.

This issue is again solved with relocation (no gotchas!):

Before (fixed) After 
class SomeType
{
public:
  // some parameterized constructor
  // SomeType(...)

  SomeType(SomeType&&) = default;

private:
  std::string _key1; /* const but cannot
    mark it so because of the
    move constructor */
  std::string _key2; /* same as _key1 */

  int _val;
};

class SomeType
{
public:
  // some parameterized constructor
  // SomeType(...)

  SomeType(SomeType reloc) = default;

private:
  std::string const _key1;
  std::string const _key2;
  int _val;
};

See how the code becomes clearer: class invariant can be written in the code instead of comments, which leads to a code that is both more readable and robust.

2.2. memberwise_trivially_relocatable is not a solution

C++26 introduces memberwise_trivially_relocatable. This form of relocation which only affects objects that live in dynamic storage, and only support trivial relocation, proves to be an incomplete solution. It is precisely providing support for both automatic storage objects and non-trivial relocation which enables us to bring the benefits we described. If either of those is missing, we cannot have:

  • always valid-types ;

  • simplified class writing ;

  • and decoupled opportunities for constant objects.

Indeed, those benefits can only emerge if we can write a non-immovable class without a move constructor. If we only supported dynamic storage objects, then such types could never be handled in automatic variables, creating a serious discrepancy (farewell std::box).

Support for trivial relocation only is also not an option. The primary concern is that of composability; an aggregate of a self-referential type that cannot be trivially relocated (e.g. std::string or std::list in some implementations) and a relocate-only type (e.g. a future std::box) can neither be relocated by move-and-destroy nor trivially relocated. (e.g. std::pair<std::string, std::box<int>> could never be relocated in some implementation, not even moved). Thus non-trivial relocation emerges as a requirement.

2.3. Pave the way to linear type support (higher RAII)

C++ does not support linear types, and this proposal does not aim to provide support for it. However it has been pointed out by Sidney Cogdill that this proposal is a big step to bring support for linear types in the language. This is a happy accident, as it was not initially intended.

A few other languages, such as Vale, support linear types. The Vale language highlights this feature as higher RAII. Another blog post lists all the benefits of such types.

To briefly summarize them:

  • a linear type may have several destructors ;

  • a linear object is an object that must be destroyed explicitly, or else the program is ill-formed.

The benefits of this approach is that, if an object requires some action to be taken before its destruction, then that action can be realized in one of its destructors and can never be forgotten by the developer, as a destructor must be explicitly invoked.

For instance, imagine you have a DBTransaction class, with two destructors: commit or rollback. You are then ensured that every transaction in the code will either be committed or rolled back, and none will be forgotten. To get a more complete view of linear types, the reader is encouraged to read the mentioned blog posts.

The current proposal brings C++ closer to linear type support because object decomposition offers an alternative way to end the lifetime of an object, without going through a destructor. The DBTransaction class we mentioned earlier could then be implemented:

struct DBTransaction
{
// [...] data members and other functions

    void rollback(this DBTransaction self reloc)
    //                                    ^ marks the decomposition of self
    {
        self._cxn.rollback();
        // as self is decomposed, its destructor is not invoked
        // (but all its subobjects are still destroyed)
    }
    void commit(this DBTransaction self reloc)
    //                                  ^ marks the decomposition of self
    {
        self._cxn.commit();
        // as self is decomposed, its destructor is not invoked
        // (but all its subobjects are still destroyed)
    }
    ~DBTransaction()
    {
        _cxn.rollback();
    }
};

void foo(DBTransaction transaction)
{
    (reloc transaction).commit();
}

A future proposal could build upon this one and introduce full linear type support. It could do so by:

  • adding an extra contextual keyword in the class definition to define a class as linear (e.g. class DBTransaction linear), and ;

  • by stating that the destructor of this class is never implicitly called (except during stack-unwinding) and the program is ill-formed if the instance is not destroyed explicitly or relocated.

2.4. Teachability

It is a matter of some confusion for learners that a "moved-from" object still exists and is accessible, but has an unspecified state. This leads to so-called "use-after-move" bugs, and requires static analysis passes and coding guidelines to prevent. "What does std::move do?" is, regrettably, a common "gotcha" question in a certain style of coding interview. In this matter C++ compares unfavorably to other languages where the "move" operation is destructive (if trivial) and bars further access to the source object.

3. Nomenclature

We refer to the Terms and definitions of the C++ Standard, and to nomenclature introduced therein, in particular the object model. In addition, we define:

3.1. Source and target objects

Relocation is the act of constructing a new instance while ending the lifetime of an existing one. This allows destructively stealing its resources, if any.

The new instance is called the target object. The existing instance whose lifetime is ended and whose resources are stolen is called the source object.

3.2. Early destructible

The lifetime of function parameters is implementation-defined in C++, but it is of most importance with relocation. Depending on the function call convention or ABI, the function may or may not be in charge of the lifetime of its parameters.

An object is said to be early destructible with regards to a function f if:

  • the object is a local variable of f, not ref-qualified, and with automatic storage ;

  • or the object is a parameter of f, passed by value, and that f has control over its lifetime ;

  • or the object’s destructor is a no-op.

We denote two main parameter passing conventions:

  • caller-destroy: the call site is in charge of the lifetime of the value parameter passed in the function call ;

  • callee-destroy: the function itself is in charge of the lifetime of its value parameters ;

Depending on the ABI choice, the convention can be per parameter, or apply to all the function parameters. Other conventions may exist, and they are still compatible with this proposal.

For instance, in a function with caller-destroy convention, none of its value parameters are early destructible. Likewise, with callee-destroy, all of its value parameters are early destructible. And last, regardless of the convention, all not ref-qualified, local variables with automatic storage are early destructible.

4. Comparison with existing proposals

This proposal introduces the reloc keyword, which allows users to explicitly and safely relocate local variables in their code base.

This proposal is also one of the few (with [P0308R0]), to tackle the case of relocate-only types. The reloc keyword thus becomes necessary to safely pass around such objects in user code.

Also, all these proposals (but [P0308R0]) aim to optimize the move and destruct operations into a single memcpy. But there are places where this optimization could not happen, and we are left with suboptimized move constructor and destructor calls.

The relocation constructor that we propose offers a customization point, and especially allows for a more optimized relocation technique than move and destruct. If trivial, then it can be optimized into a memcpy.

4.1. P0023R0: Relocator: Efficiently moving objects by Denis Bider

The Relocator introduced in [P0023R0] is similar to the proposed relocation constructor. However P0023R0’s Relocator is not viewed as a constructor. Instead, it is a special function that can be invoked in lieu of move plus destroy where possible.

However this brings again suboptimal support for relocate-only types. Indeed [P0023R0] does not force relocation to happen in all cases, and falls back to move+destroy paradigm when relocation cannot happen.

A typical example is when relocating a function parameter:

void sink(T);
void foo(T x) { sink(x); }

Here, under the terms of [P0023R0], relocation may not happen because of ABI constraints (if x is not early destructible). This will cause foo to fallback to a move+deferred destroy paradigm.

This proposal has another take on this issue: if T has a relocation constructor but no move constructor, then any function that takes a T parameter by value is required to have an ABI that allows it to relocate its input parameter (e.g. callee-destroy ABI).

This proposal also introduces the reloc keyword that is here to trigger the relocation, and protect against the reuse of the relocated object. The solution then becomes:

void sink(T);
void foo(T x) { sink(reloc x); /* x can no longer be used. */ }

Moreover, the proposed syntax for invoking [P0023R0]’s relocator is low-level and prone to error:

T x;
alignas(T) char buf[sizeof(T)];
T* y = new (buf) >>T(x);

Here the lifetime of x has been ended as if by a destructor call, but the language is not aware of this, so firstly the user may erreoneously refer to x as if it was within its lifetime, and secondly if an object is not recreated in x by the time the block exits, the behavior is undefined by [basic.life]/9. Likewise, the language is not aware of the existence of *y so will not call its destructor; the behavior is then possibly undefined under [basic.life]/5. In contrast, the present proposal would write the above as:

T x;
T y = reloc x;

Here the use of the reloc keyword ensures that the language is aware that the lifetime of x has finished, so the destructor only of y is called at scope exit.

4.2. N4158: Destructive Move by Pablo Halpern

[N4158] proposes a customizable function std::uninitialized_destructive_move, that is somewhat similar to the relocation constructor, but is a pure library solution.

It has several drawbacks :

  • relocation can only happen if this function is called explicitly. Typically this function would be called in container implementation. But then we cannot relocate local variables with this.

  • users can write their own uninitialized_destructive_move overload, but this is terrible for composability. Classes that have a subobject with a custom uninitialized_destructive_move overload do not get a uninitialized_destructive_move overload generated for free.

  • uninitialized_destructive_move cannot be default-generated with memberwise relocation.

4.3. P1029R3: move = bitcopies by Niall Douglas

[P1029R3] enables a special bitcopies move constructor for types that are trivially relocatable.

We have already pointed out that trivial relocation is not enough. Because of that point alone, it does not solve any of the issues we mentioned.

4.4. P0308R0: Valueless Variants Considered Harmful by Peter Dimov

We only consider the "pilfering" proposition from [P0308R0]. P0308R0’s pilfering shares some similarities with the current proposal, as it is an attempt to support relocate-only types as a pure library solution.

We believe a language solution is best suited here:

  • the source object is effectively destroyed by the relocation: its destructor is not called. This can hardly be achieved by a library solution ;

  • the reloc keyword makes sure the relocated object is not reused, while std::pilfer does not ;

  • the pilfering constructor is inconvenient to write as we need to unwrap from std::pilfered and rewrap to propagate to base classes and data members ;

  • as a library solution, the pilfering constructor cannot be defaulted ;

  • trivial relocation is not possible with pilfering, which makes [P0308R0] miss the performance boost that is so longed for.

4.5. D2839R1: Nontrivial Relocation via a New owning reference Type by Brian Bi and Joshua Berne

[D2839R1] is very close in spirit and mechanism to this paper. We consider the addition of an "owning reference" to be an unnecessary complication to the type system that would impose a burden throughout library code. We refute the claim that a prvalue occupying storage constitutes a fourth value category; in our model, the lvalue that previously occupied that storage ceases to exist and a new prvalue is formed, which may come to occupy that storage (if relocation is elided) or distinct storage (in the general case).

We are intrigued by the claim that an owning reference can provide superior performance when passing a variable up the stack, compared to repeatedly relocating it from caller to callee, but believe that in practice such gains would be minimal and liable to be eliminated via optimization, while our model offers the possibility of improved locality, since the relocated object will reside directly in the leafmost function’s stack as opposed to being accessible only via indirection. Alternatively, this concern can be regarded as an implementation choice. Implementations where only the address of the object is passed down from caller to callee are still possible with our model.

Otherwise, the paper has some minor differences in naming (e.g. std::force_relocate for what we call std::reloc_and_uninitialize) that could easily be reconciled in either direction.

5. Proposed language changes

5.1. reloc operator

This paper suggests to introduce a new keyword, named reloc. reloc acts as a unary operator that can be applied to named, local, complete objects (in other words: function-local non-static variables and, with some restrictions, function parameters and identifiers introduced through the syntax of structured binding declarations).

reloc obj does the following:

  • if obj is ref-qualified, then performs perfect-forwarding (as if by static_cast<decltype(obj)>(obj)) ;

  • otherwise returns a temporary obtained from the source object, constructed from the relocation, move or copy constructor.

    • If the relocation constructor was called, then the source object has been destroyed.

    • If not, then the destructor of the source object will be implicitly invoked as soon as the implementation permits, if possible at the end of the full-expression evaluation ;

  • in all cases, marks the "early" end-of-scope of the variable obj, preventing reuses of the variable.

5.1.1. reloc to perfectly forward all value categories

reloc can be used on ref-qualified objects to enable perfect forwarding. If the source object is ref-qualified, then it performs the following cast: static_cast<decltype(obj)>(obj).

This makes reloc the one operator to use to perfectly forward objects, whether they are ref-qualified or not. It also prevents from use-after-move and use-after-relocation errors.

5.1.2. reloc in constexpr

reloc can be used in constexpr functions and constant-evaluated expressions.

5.1.3. reloc produces a prvalue

Unlike std::move, reloc does perform some form of relocation. Through misuse of language, we say that reloc returns a temporary object, created by relocation, move or copy constructor. In truth, given that the source object is not ref-qualified, reloc merely changes the value category of the source object from lvalue to prvalue (if the source object is ref-qualified, see above). The prvalue produced by reloc occupies the same storage as that of the source object.

It is this value category change that may trigger the creation of a temporary object. However, optimizations may happen that will elide the creation of the temporary entirely.

If the temporary is materialized, then it is ideally constructed by the relocation constructor, destroying the source object in the process. However, reloc does not force the use of the relocation constructor. The constructor which will be used to create the temporary is selected by overload resolution. reloc merely enables the relocation constructor to be selected because of the value category change (the relocation constructor has the signature T(T reloc), meaning it will be preferred when constructed from a prvalue, with our new overload resolution rules).

5.1.4. Relocation constructor discardment with function parameters

Function parameters' lifetime ownership is implementation-defined in C++. Depending on the ABI in use, a function parameter may be destroyed at caller-site (upon function return, at the end of the full-expression evaluation), or at callee-site (before the function exits).

Enforcing the relocation constructor when reloc is used on a function parameter, which would effectively destroy the function parameter, will not be compatible with all existing ABIs (see Itanium ABI for instance). We could propose this nonetheless, by stating that the relocation constructor must be used if declared. However we fear this would propagate ABI changes with too little control and the proposal would meet too much resistance to go further.

We could take a very conservative approach, and mandate the ABI change for relocate-only value parameters. Such types don’t exist today, so the likelihood of breaking any existing ABI is relatively small. However this may lead to suboptimized code, where reloc would perform worse than move semantics. Consider now the following code:

With move semantics With relocation 
struct A
{
    // [...]
    A(A const&) = default;
    A(A&&) = default;
};

void bar(A);
void foo(A a)
{
    bar(std::move(a));
}

struct A
{
    // [...]
    A(A const&) = default;
    A(A&&) = delete;
    A(A reloc) = default;
};

void bar(A);
void foo(A a)
{
    bar(reloc a);
}

Since A has a copy constructor, it is not relocate-only. With the conservative approach, we have no guarantee that foo has the ownership of a. Hence reloc a here may simply call the copy constructor, as the ABI may not permit otherwise.

To prevent such a pessimization, developers will be tempted to add a move constructor to A, ensuring that at least the move constructor is called in such cases. Doing so goes against what we are trying to achieve with this proposal. One of our main motivation points is that the move constructor doesn’t fit all classes that could yet still be moved. We don’t want users to declare one anyway to avoid pitfalls.

Thus in an attempt to make a compromise between ABI compatibility and acceptable support for relocation, we take a slightly less conservative approach. We would like function parameters passed by value, whose type declares a relocation constructor but no move constructor, to be early destructible. As the C++ standard leaves this area implementation-defined, we are going to force this another way, although the effect is the same:

Rule: In a temporary materialization, if the reloc operand is a function parameter passed by value, and its type provides an eligible move constructor, then the relocation constructor (if any) may be discarded during overload resolution. Whether the relocation constructor is discarded is implementation-defined.

Note: eligible is defined in [special].

As consequences of that rule, we get the following:

  • early destructible source objects are always guaranteed that their relocation constructor (if eligible) is called ;

  • source objects which are not early destructible, and have both an eligible move and relocation constructor, will not be relocated. Instead the move constructor will be invoked by reloc.

  • source objects which are function parameters, and have an eligible relocation constructor but no move constructor, are forcibly early destructible.

NOTE: Types which have a relocation constructor but no move constructor still don’t exist today, so the likelihood of breaking existing ABIs is still small.

With this updated rule, reloc a from our previous example will effectively call the relocation constructor. And users can safely migrate away from the move constructor to the relocation constructor if they wish to without any gotchas.

Note that this rule still isn’t optimal. Consider the following code, having in mind a putative std::pair with a relocation constructor:

void bar(pair<const string, int>);

void foo(pair<const string, int> val)
{
    val.second *= 2;
    bar(reloc val);
}

std::pair has the three constructors, so our rule does not apply. The ownership of val by foo is implementation-defined. If foo doesn’t own val, then reloc val will call the move constructor, making a full string copy (because of const). Contrary to our previous example which motivated us to update the parameter ownership rule, here reloc may call std::move so we haven’t worsened the situation.

5.1.5. Early end of scope

As we have seen reloc may trigger a call to the relocation constructor. At the moment of the call, the lifetime of the source object has ended. Thus it is unsafe to reuse it after the reloc expression completes.

To prevent uses of a potentially destructed object, we state that the program is ill-formed if the source object is reused after being passed to reloc, regardless of whether the relocation constructor was called. For a detailed explanation of how this is enforced, please refer to the dedicated section.

NOTE: The rest of this section only applies to reloc operands that are not ref-qualified.

That early end of scope provides us with a strong guarantee. We know that the source object cannot be reused, and as such we may be tempted to call the destructor of the source object early (in cases where the relocation constructor was not selected). For instance, we may want to destroy the source object at the end of the full-expression evaluation, when temporaries are destroyed. It would be the natural thing to do:

  • for consistency, if the object had been relocated (with the relocation constructor), then it already reached its end of life. The same could be expected for copy and move constructor ;

  • the source object cannot be reused anyway, why defer its destruction?

Unfortunately this cannot be done without breaking some ABIs, especially because the source object may not be early destructible. Let us see what happens if we allow the early destruction of function parameters to be implementation-defined:

  • If reloc calls the copy constructor: all the resources owned by the source object are copied to the target object. As such if the destructor has side-effects, they will be applied twice, once for the destruction of each object. Depending on the ABI, the destructor of the source object may be called at the end of full-expression, or deferred until control returns to the caller. We can see that the destruction time of the source object would be implementation-defined (as of today). Remember that we might have side-effects from the destructor, so the moment those side-effects will be applied will also be implementation-defined.

  • If reloc calls the move constructor: all the resources owned by the source object are transferred to the target object. As such if the destructor has side-effects, we expect them to be applied only once, at the destruction of the target object. We expect the source object destructor to detect the moved-from state and return, without triggering any side-effects. Under those reasonably safe assumptions, it doesn’t matter when the source object is destroyed, be it at its natural end of scope, or at the end of the reloc full-expression.

As of today, the lifetime of function parameters is already implementation-defined. As such, code that relies on the timing of a destructor side-effects of a function parameter is already implementation-defined. We don’t feel we will worsen the situation with reloc, even with copy-only source objects. We prefer to keep this behavior implementation-defined, same as today, except that the source object may also be destructed early, at the end of the full-expression evaluation that contained reloc.

In conclusion, we establish the following rule when a reloc expression is evaluated:

Rule: If a reloc operand (the source object) is not relocated by its relocation constructor, and:

  • the source object is not a function parameter: then its lifetime ends (i.e. its destructor is implicitly invoked) at the end of the full-expression evaluation containing the evaluated reloc expression ;

  • the source object is a function parameter: then its destructor must be implicitly invoked at the end of the full-expression containing the evaluated reloc expression, or at the caller site at the end of the full-expression evaluation. Which it is is implementation-defined.

We acknowledge that with reloc expressions we allow for more code to be executed between the end of the full-expression which contained reloc, and when control returns to the caller site. One might argue that we exacerbate this destruction time discrepancy between implementations. However please keep in mind that:

  • this only concerns copy-only value parameters, whose destructor have a side-effect, and are passed to reloc ;

  • any arbitrary amount of code could still be executed today upon function exit, at the end of the full-expression evaluation that made the function call, at caller-site. Indeed, all function parameters need to be destructed, and their destruction order remains implementation-defined as of today, leaving the door open for any arbitrary code from a destructor, to be executed before the destructor of our source object ;

  • code that relies on a precise destruction timing of a function parameter must be avoided as this timing is implementation-defined, even today.

5.1.6. Illegal uses of reloc

A reloc expression is ill-formed if any of the following conditions is met:

  • its parameter is not the name of a variable, or a direct subobject of a decomposed object ;

  • the source object is not a complete object ;

  • the source object is not ref-qualified and does not have local storage (i.e. not a local function variable and not a function parameter passed by value) ;

  • the source object is not ref-qualified and does not have an accessible relocation, move, or copy constructor. Exception: if the source object is not a function parameter, and the reloc expression is discarded, then the source object is permitted to have none of the 3 constructors ;

  • the source object is a structured binding (and not an identifier introduced in a structured decomposition declaration) ;

  • the source object is a lambda capture (unless the lambda closure object has been decomposed) ;

  • the source object is a virtual base of a decomposed object ;

In particular, the reloc expression is well-formed if the source object is a member of a function-local anonymous union.

For instance:

void foo(std::string str);
std::string get_string();
std::pair<std::string, std::string> get_strings();

std::string gStr = "static string";

void bar(void)
{
    std::string str = "test string";
    foo(reloc str); // OK: relocation will happen given that std::string has a reloc ctor
    foo(reloc gStr); // ill-formed: gStr does not have local storage

    std::pair p{std::string{}, std::string{}};
    foo(reloc p.first); // ill-formed: p.first is not a complete object (p should have been decomposed)

    foo(reloc get_string()); // ill-formed: not the name of variable
    foo(reloc get_strings().first); // ill-formed: not a complete object, and not the name of variable
}

void foobar(const std::string& str)
{
    foo(reloc str); // OK: str is passed by reference.
    // Note that the lifetime of the referent of str is unaffected.
}
void foobar(std::string* str)
{
    foo(reloc *str); // ill-formed: *str is not the name of variable
}
void foobar2(std::string* str)
{
    foobar(reloc str); // OK, the pointer itself is relocated (not the pointed value)
}

class A
{
    std::string _str;
public:
    void bar()
    {
        foo(reloc _str); // ill-formed: _str is not a complete object and does not have local storage
    }
};

5.1.7. Discarded reloc expressions

This section discusses the effect of discarded reloc expressions in cases where its operand is not ref-qualified. Such an expression is for instance reloc obj;

We propose such expressions to have the same effect as { auto _ = reloc obj; }. A temporary is constructed from the source object and is then destructed at scope exit (that is right-away). The source object is destructed right-away, or at later stage if it’s a function parameter (when exactly is implementation-defined). We will discuss here the effects of such expressions.

Materializing a temporary whose only goal is to be destroyed is suboptimal. We might be tempted to optimize away the temporary materialization, and only call the destructor of the source object.

This optimization is mandatory if the source object is immovable (none of the three constructors are eligible) and not a function parameter. In other cases, this optimization remains authorized (whether it is performed is implementation-defined). If the optimization cannot happen, then the temporary must be materialized and destroyed at the end of full-expression evaluation. The lifetime of the source object follows the established rules.

Note that, if the temporary is materialized and that the source object:

  1. has an eligible relocation or move constructor: In this case, all the owned resources of the source object will be transferred to the temporary. For this reason, we expect that destroying the temporary will have the same effects as destroying the source object directly.

  2. only has an eligible copy constructor: all the owned resources of the source object will be copied to the temporary. This is very likely a useless operation.

  3. Other cases need not to be considered, as if materialized, the reloc expression requires the source object to declare one of the three constructors.

NOTE: If the source object is a copy-only function parameter, then implementations are encouraged to emit a warning on discarded reloc statements, as if reloc had the [[nodiscard]] attribute. This is because the intent of this statement is likely to trigger the destruction of the source object (or to trigger the effect of the destructor, if a move-constructed temporary is materialized and destroyed). But whether this statement indeed calls a destructor early (or has any side-effect) for copy-only function parameters is implementation-defined.

To summarize, it means that reloc obj; has the following behavior:

  • If obj is early destructible then:

    • The temporary is likely elided, effectively only calling the destructor of obj.

    • Otherwise a temporary is initialized from the source object, and then destructed.

  • Otherwise:

    • A temporary is move-or-copy-constructed and then destructed.

    • The source object destruction is deferred until the function returns.

For instance this gives:

void do_something_01(std::lock_guard<std::mutex> guard)
{
    if (!some_test())
    {
        reloc guard; // ill-formed: no relocation, move or copy constructor
        log("thread ", std::this_thread::get_id(), " failed");
        return;
    }
    bar();
}
void do_something_02(std::mutex& m)
{
    std::lock_guard guard{m};
    if (!some_test())
    {
        reloc guard; // well-formed: direct destructor call is forced to happen
        log("thread ", std::this_thread::get_id(), " failed");
        // ^ logging can happen without holding the lock
        return;
    }
    bar();
    /* guard destructor is called */
}
void do_something_03(std::unique_lock<std::mutex> guard)
{
    if (!some_test())
    {
        reloc guard; /* well-formed: lock is released, either by calling the
            destructor directly, or by constructing a temporary from
            guard (by relocation or move) and destructing it. */
        log("thread ", std::this_thread::get_id(), " failed");
        return;
    }
    bar();
}
void do_something_04(std::mutex& m)
{
    std::unique_lock guard{m};
    if (!some_test())
    {
        reloc guard; /* well-formed: temporary is likely elided regardless of
            do_something_03's ABI, only calling the destructor of guard. */
        log("thread ", std::this_thread::get_id(), " failed");
        return;
    }
    bar();
    /* guard destructor is called */
}
// assuming non_null does not have a relocation constructor
void do_something_05(non_null<shared_ptr<int>> copyOnlyObj)
{
    if (!some_test())
    {
        reloc copyOnlyObj; /* well-formed but its effects are implementation
            defined. Will emit a warning. */
        return;
    }
    bar();
}

5.1.8. Relocation elision

Relocation may be elided. This is intended to work in much the same way as the named return value optimization; for example:

void f(std::string s);
void g() {
    std::string s;  // may be created in f's argument slot
    f(reloc s);  // relocation may be elided
}

More formally, whether performed by relocation, move or copy constructor, the temporary created by the reloc expression may not be materialized if the implementation can ensure that the source object shares the same address as the one to be occupied by the target object.

Of course, if relocation elision happens then the rules that impact the lifetime of the source object still applies.

For instance, given the following function void sink(T), let us observe the effects of the sink(reloc obj) expression (obj being not ref-qualified) across different ABIs and object lifetime ownerships:

  • If obj is early destructible and sink is callee-destroy: relocation elision may happen, in which case obj occupies the same storage as sink parameter slot. No new instance is created, and as sink is callee-destroy, it will take care of the lifetime of obj.

  • If obj is early destructible and sink is caller-destroy: relocation elision may happen, in which case obj occupies the same storage as sink parameter slot. No new instance is created. As sink is caller-destroy, the destructor of obj is implicitly invoked at the end of the full-expression evaluation which invoked sink.

  • If obj is not early destructible and sink is caller-destroy: relocation elision may not happen. Right before the invocation of sink in the expression sink(reloc obj), obj is expected to be in a moved-from state. Indeed, because it is not early destructible, reloc will invoke the move constructor, and the destruction of obj is deferred until control returns to the caller-site. But should elision happen, hence bypassing the call to the move constructor, then obj cannot be left in its moved-from state... Hence if obj is not early destructible, then relocation elision cannot happen.

  • If obj is not early destructible and sink is callee-destroy: this configuration cannot happen in practice.

Likewise, we can observe when elisions are possible given the following function void xvsink(T&&), invoked through the xvsink(reloc obj) expression:

  • If obj is early destructible: relocation elision may happen, in which case an rvalue reference of obj is sent to xvsink and the destructor of obj is implicitly invoked at the end of the full-expression evaluation.

  • If obj is not early destructible: Same as above. When obj is not early destructible, then relocation elision loses its interest. A new instance is move-or-copy-constructed from obj, whose rvalue reference is passed to xvsink.

The same kind of elision will happen with an lvsink(T const&) function: elision can only happen when the source object is early destructible.

You can read more on relocation elision in the discussion section.

5.2. Object decomposition

This proposal introduces the concept of object decomposition. Only complete objects can be decomposed. An object is decomposed if the reloc keyword appears in its definition. If an object is decomposed, then it ceases to exist, but all its subobjects are considered as complete objects.

Decomposition is an alternative way to end the lifetime of an object.

5.2.1. Declaration and definition

5.2.1.1. Object definition

In an object definition, the reloc keyword can be specified after the object name:

T const value reloc = getValue();

reloc cannot be used in an object declaration or else the program is ill-formed. Note that reloc is not part of the C++ type system. This is emphasized by the fact that reloc can only be specified after the object name.

reloc can only be used in an object definition (with T the type of the object being defined) if:

  • the object is a complete object with automatic storage ;

  • the object is a function parameter or a function-local object ;

  • T is a non-union class-type ;

  • T is not ref-qualified.

If any of the above conditions is not verified, then the definition is ill-formed. For instance:

struct X
{
    std::pair<int, std::string> m reloc; // ill-formed
};

static std::pair<int, std::string> g reloc; // ill-formed

void foo(T const& a reloc) {} // ill-formed (ref-qualified)
void foo(T const* a reloc) {} // ill-formed (not a class-type)
void foo()
{
    T const a[] reloc = { }; // ill-formed (not a class-type)
}

// But
void foo(T const obj reloc) // well-formed if T is a class-type
{
    T obj2 reloc; // well-formed if T is a class-type
}

If several objects are declared in the same expression, then reloc needs to be repeated for each object which the user wants to decompose:

T const value reloc = getValue(0), value2 = getValue(1), value3 reloc = getValue(2);
// only "value" and "value3" are decomposed.
T const c, *d reloc; // ill-formed, d is not a class-type
5.2.1.2. Function declaration and definition

Functions parameters may be declared with reloc, in which case the parameter is declared as decomposed.

The reloc specifier does not produce a new overload of a function: f(T) and f(T reloc) refer to the same function.

If a function parameter is declared as decomposed, it needs to be done so for every visible function declaration and its definition. In our previous example f(T) and f(T reloc) refer to the same function, but they have conflicting declarations, making the program ill-formed.

Indeed, the decomposed parameter may be used in contract expressions (which must be identical across all visible function declarations), and the fact it’s decomposed has a direct impact on the well-formedness of the contract expressions that use it.

The parameter decomposition trait may not be attached to a function pointer. As with contracts, the decomposition trait has no impact on the function type, and thus no impact on the type of its address.

When a function which decomposes one or more of its parameters is invoked through a function pointer, the parameter decomposition must still be honored.

void foobar(T obj reloc);

void foobar(T obj) // ill-formed, not matching its declaration
{}

void foobar2(T obj);
void foobar2(T obj reloc); // ill-formed, not matching previous declaration

struct X
{
    void foo(T obj reloc);
    void bar(T obj);
};

void X::foo(T obj reloc) // well-formed
{}

void X::bar(T obj reloc) // ill-formed, not matching its declaration
{}

static_assert(std::is_same_v<decltype(&X::foo), void (X::*)(T)>); // ok

5.2.2. Decomposition operation

When a complete object is defined as decomposed, then:

  • The object is initialized using the existing rules ;

  • All its direct bases and non-static data members are now considered as distinct complete objects:

    • the decomposition does not odr-use any of the copy, move or relocation constructor of the subobjects. In particular, their address remains unchanged ;

    • for all of the virtual and direct bases which have a runtime type information, they now point to that of the base class, and no longer point to the type of the decomposed object. This step is identical as to what happens with the runtime type information of base classes once the destructor body is executed ;

    • all virtual bases, if any, keep the same address ; all pointers to such virtual bases remain unchanged ;

    • the introduced objects (i.e. the subobjects of the decomposed object) have the same lifetime as the decomposed object, had it not been decomposed ;

    • the introduced objects still inherit from the cv-qualifiers, if any, of the decomposed object.

  • The lifetime of the decomposed object ends: its destructor is never invoked implicitly. All its non-static subobjects, now considered as complete objects, have a lifetime of their own.

Note: If not for changing the runtime type of the direct bases that have one, the decomposition operation would be a no-op.

For instance:

void foo(std::pair<std::string const, int> kv reloc)
{
    // kv object no longer exists
    // its subobjects are accessible through the decomposed object "kv"
    bar(kv.second, reloc kv.first);
    // kv.second destructor will be invoked implicitly
}

struct B { int _b; };
struct D : B { std::string _d; };
void foo(D const d reloc)
{
    // d.B designates the base of former d object
    static_assert(std::is_same_v<decltype(d.B), B>);
    static_assert(std::is_same_v<decltype(d._d), std::string>);
    bar(reloc d.B); // well-formed
}

5.2.3. Illegal decomposition

The decomposition of an object src of type T is ill-formed if any of the following conditions is not satisfied:

  • all subobjects of src are accessible. They all need to be since their destructor will be called if not relocated ;

  • all declared special member functions of T are declared either as defaulted or deleted, or the call-site has private access privilege to T.

These requirements ensure that we can only decompose (a) compound types, where subobjects have no dependencies with one another (like an std::pair), or (b) types that we are in control of (because of the private access).

An additional requirement applies if the object to decompose is a function parameter. In that case, T must have an eligible relocation, move or copy constructor. This extra requirement is to make object decomposition available for function parameters regardless of the ABI.

5.2.4. Decomposed objects in expressions

A decomposed object is not an object. You should think of the decomposed object as if it were a special namespace holding all its former subobjects. The decomposed object can be used in expressions as a proxy to access its former subobjects.

The id-expression naming the decomposed object does not yield a value! (unless it is used in an unevaluated operand).

A decomposed object is used in expressions:

  • to access a former data member ;

  • to access a former base ;

  • to call a static member function ;

  • to access a former data member through a constant-evaluated pointer to data member ;

  • as an unevaluated operand of sizeof, typeid or decltype.

NOTE: In particular, non-static member functions cannot be called from a decomposed object. Such expressions are ill-formed.

5.2.4.1. Accessing a data member of a decomposed object

The data member of a decomposed object can be accessed through the expression:

decomposed-object . data-member

Such expressions are identical to the matching expression had the object not been decomposed:

  • it yields exactly the same result (same type, same value category) ;

  • if the data member is not a direct data member of the decomposed object type, then base classes are looked-up for a matching data member. If there are no matching data members, several matching data members, or the matching data member is inaccessible, then the expression is ill-formed.

  • The expression returns a complete object if the data member is a direct data member of the decomposed object. Otherwise the returned object cannot be relocated without decomposing its owner class first.

  • The data-member expression may not contain disambiguation expressions.

For instance:

struct B
{
    int _b_pub;
    int _common;
private:
    int _b_priv;
};
struct C
{
    int _common;
};
struct D : public B, public C
{
    int _d;
};

void foo(D d reloc)
{
    d._d = d._b_pub; // valid
    d._d = d._common; // ill-formed, d._common is ambiguous
    d._d = d.C::_common; // ill-formed, disambiguation is not possible
    d._d = d.C._common; // valid, see next section
    d._d = d._b_priv; // ill-formed, _b_priv is private in the context
}

NOTE: Static analysis will detect if the accessed data member is still valid, meaning whether it has already been relocated, or if non direct, whether it belongs to a base class that has been relocated.

5.2.4.2. Accessing a direct base class of a decomposed object

Any base class (even virtual and non-direct) of a decomposed object can be accessed through the expression:

decomposed-object . base-class-name

If the base class is not a direct base class of the decomposed object type, then all non-direct base classes are looked-up. If there are no matching base classes, several matching base classes, or the matching base class is inaccessible, then the expression is ill-formed.

The expression returns a complete object only if the base class is a direct base of the decomposed object. Otherwise the returned object cannot be relocated without decomposing all intermediary classes on the inheritance path.

Such expressions allow to access the base class as a data member, as if a data member named after the class had been declared in the decomposed object, sharing the same access specifier as that of its inheritance, not ref-qualified, and with no cv-qualifiers.

You might think such expressions are identical to the following expression, had the object not been decomposed:

static_cast<B cv &>(obj)

with B being the base class to access, and cv the cv-qualifiers that apply to the decomposed object. One notable difference though, is that the type of the static_cast expression is ref-qualified, while the type of decomposed-object . base-class-name expression is not.

For instance:

struct A { int _a; };
struct B : public A { int _common; };
struct V { int _v; };
struct C : public virtual V { int _common; };
struct D : public B, public C
{
    int _d;
};

void foo(D d reloc, D const d_const reloc)
{
    std::println(d.C._common); // valid
    std::println(d.B._common); // valid
    std::println(d.V._v); // valid
    std::println(d.A._a); // valid, d._a is also okay

    static_assert(std::is_same_v<B, decltype(d.B)>);
    static_assert(std::is_same_v<B&, decltype((d.B))>);

    static_assert(std::is_same_v<B, decltype(d_const.B)>);
    static_assert(std::is_same_v<B const&, decltype((d_const.B))>);
}

NOTE: Static analysis will detect if the accessed base is still valid, meaning whether it has already been relocated, or if non direct, whether it belongs to a base class that has been relocated.

5.2.4.3. Addressing static members from the decomposed object

Static data members and static member functions can be accessed from a decomposed object as if the object had not been decomposed, reusing today’s syntax.

struct D
{
    static void func();
    static int _data;
};

void foo(D d reloc)
{
    d.func(); // well-formed
    std::invoke(d.func); // well-formed
    auto i = d._data; // well-formed
}
5.2.4.4. Accessing a data member of a decomposed object through pointer

A data member of a decomposed object can be accessed by a constant-evaluated pointer to data member through the expression:

decomposed-object . * pointer-to-data-member

If the pointer to the data member is not constant-evaluated, then the expression is ill-formed. Had the pointer been allowed not to be constant-evaluated, then it would have been difficult for static analysis to know if the pointed data member is still valid (i.e. whether it has been relocated), and more importantly whether the pointed data member is a direct data member or one that belongs to a base class.

Again, such expressions are identical to the matching expression had the object not been decomposed.

For instance:

struct B
{
    int _b_pub;
    int _common;
private:
    int _b_priv;
};
struct C
{
    int _common;
};
struct D : public B, public C
{
    int _d;
};

void illformed(D d reloc, int D::* data)
{
    d.*data = d._d; // ill-formed, data is not constant-evaluated
}
consteval void valid1(D d reloc, int D::* data)
{
    d.*data = d._d; // valid
}
template <int D::* Ptr>
void valid2(D d reloc)
{
    d.*Ptr = d._d; // valid
}
void valid3(D d reloc)
{
    constexpr int D::* a = &B::_d;
    d.*a = d._d; // valid
}
5.2.4.5. Decomposed object as an unevaluated operand

The id-expression designing a decomposed object may be used as operand of the operators sizeof, typeid and decltype. The three operators yield the same result as if the object had not been decomposed, with just a few specificities:

  • If obj is the decomposed object, then typeid(obj) is equivalent to typeid(decltype(obj)) (the RTTI if any is not inspected) ;

  • As (obj) is an ill-formed expression if obj is a decomposed object, decltype((obj)) is also ill-formed.

  • decltype(obj.member_function()) is also ill-formed.

5.2.4.6. Other expressions with a decomposed objects

Any the expression involving a decomposed object that is not covered in the subsections above is ill-formed.

In particular, with obj being a decomposed object, the evaluations of the following expressions are ill-formed:

  • (obj): obj is not an object, the expression does not produce a value.

  • foo(obj): same as above.

  • (obj).m (with m being a data member): same as above.

  • (obj, a).m (with a being an object of same type): obj expression does not produce a value, it cannot be used as operand in the comma operator.

  • (a, obj).m: same as above.

  • auto x = (obj, a): same as above.

This is a direct consequence of the obj expression not yielding a value.

5.2.5. Decomposed subobjects in reloc expressions

The direct subobjects of a decomposed object can be used as the operand of reloc expressions. As such objects are complete objects, the reloc expression has the same effect as described in the reloc operator section.

The only exception to the above is if the reloc operand is a virtual base of a decomposed object. Virtual bases cannot be safely relocated, and hence their relocation is ill-formed (see below).

For instance:

struct A { int _a; };
struct B : public A { int _b; };
struct V { int _v; };
struct C : public virtual V { int _c; };
struct D : public B, public C
{
    int _d;
};

void foo(D obj reloc)
{
    auto d = reloc obj._d; // valid
    // auto c = reloc obj._c; //< ill-formed, _c is not a direct data member of D
    // auto a = reloc obj.A; //< ill-formed, A is not a direct base of D
    auto b = reloc obj.B; // valid
    // auto b2 = obj._b; //< ill-formed, obj._b belongs to B base which has been relocated
    auto c = reloc obj.C; // valid, but obj.V is in a moved-from state after
    // auto v = reloc obj.V; //< ill-formed, V is a virtual base of D
    auto v = std::move(obj.V); // valid
}
5.2.5.1. Relocation and virtual bases

The current proposal does not support the relocation of virtual bases. Relocate-only types can hardly be a virtual base, and by extension virtual bases can hardly have relocate-only data members.

We argue that this limitation comes from the very nature of non-trivial relocation and virtual bases. Let’s consider the following snippet:

struct V { int _v; };
struct B : public virtual V { int _b; };
struct C : public virtual V { int _c; };
struct D : public B, public C
{
    int _d;
};

void foo(D obj reloc)
{
    auto c = reloc obj.C; // #1. valid, but obj.V is in a moved-from state after
    // auto v = reloc obj.V; //< ill-formed, V is a virtual base of D
    auto b = reloc obj.B; // #2. valid
}

Because of the decomposition, each subobject is now a complete object. However, because of the virtual inheritance, the virtual bases are shared across all the types that inherit from it. At #1, C’s relocation constructor will initialize its own V base, from obj.C. As obj.C does not have the ownership over its virtual base, then C relocation constructor cannot use V relocation constructor to initialize V. Instead the move or copy constructor will be used. Otherwise, had the virtual base been relocated (in C relocation constructor), then the expression auto b = reloc obj.B (#2) would have accessed uninitialized memory when it tried to initialize its own V base (in B relocation constructor).

C++ is already a language with many pitfalls ; one common source of errors is dangling references, and should virtual bases be allowed to be relocated, then it would create even more of them...

You might think that this issue arises from decomposition. In #1 and #2, we ask to create a new V instance twice. But surely it should work in the scope of a relocation constructor right? Because then only one V instance is created. But then consider the following snippet, with an amended B:

struct B : public virtual V
{
    B(B rhs reloc) : V(std::move(rhs.V)), _b(reloc rhs._b)
    {
        std::cout << rhs._v << std::endl; // #3
    }

private:
    int _b;
};

Now the default relocation constructor of D will construct V, then invoke B relocation constructor. If D initializes V with relocation semantics, then B relocation constructor will access uninitialized memory at #3!

We don’t believe this to be a blocking limitation as some mitigation remains possible, through a custom T T::exchange(T rhs) function. Such a function is recommended to be implemented for any relocate-only type (see std::box::exchange). See for instance:

struct V
{
    std::box<int> _v; // V is now relocate-only

    V exchange(V rhs reloc)
    {
        return {_v.exchange(reloc rhs._v)};
    }
};
struct B : public virtual V
{
    B(B src reloc) : V{src.V.exchange({})}, _b{reloc src._b} {}

    int _b;
};
struct C : public virtual V
{
    C(C src reloc) : V{src.V.exchange({})}, _c{reloc src._c} {}

    int _c;
};

struct D : public B, public C
{
    D(D src reloc) : V{src.V.exchange({})}, B{reloc src.B}, C{reloc src.C},
        _d{reloc src._d} {}

    int _d;
};

NOTE: You might think that tracking whether an object owns its virtual bases may be difficult. On the contrary, it’s actually straightforward: only subobjects of decomposed objects are not in charge of their virtual bases, all the rest are. See for instance:

struct V { int _v; };
struct B : public virtual V { int _b; };
struct C : public virtual V { int _c; };
struct D : public B, public C
{
    int _d;
};

void foo(D obj reloc)
{
    B b reloc = reloc obj.B;
    assert(&obj.V == &b.V);
    // None of obj.B, obj.C and b.V have the ownership over their virtual base
    C c = reloc obj.C;
    // c has the ownership over its virtual base
}

5.2.6. Getting the address of an object after its decomposition

Sometimes retrieving the address of a decomposed object is needed. For instance this may be useful in relocation constructors, to adjust some external objects:

T::T(T src reloc) : _d{reloc src._d}
{
    gRegistry.erase(/* src address */);
    gRegistry.insert(this);
}

We propose the following expression obj . this to return the address the object occupied prior to its decomposition as a prvalue, with type void cv *, cv being the cv-qualifiers that applied to obj.

  • Since the expression is a prvalue, it cannot be assigned to a new address and its own address cannot be taken (obj.this = &x and &obj.this are ill-formed). Note that this today is already a prvalue.

  • The return type is a void pointer. As the object has ceased to exist, the returned pointer cannot be a pointer of the former object type.

Hence our example becomes:

T::T(T src reloc) : _d{reloc src._d}
{
    gRegistry.erase(src.this);
    gRegistry.insert(this);
}

And we have:

{
    T obj reloc = {};
    static_assert(std::is_same_v<void*, decltype(obj.this)>);
}
{
    T const obj reloc = {};
    static_assert(std::is_same_v<void const*, decltype(obj.this)>);
}

5.2.7. Decomposition of a lambda closure type

Lambda objects can be decomposed with the rules defined above. The decomposition can only happen from the lambda body and not from outside the lambda, as if its captures had private access.

All the lambda captures are accessible through the decomposed lambda. In practice only the objects captured by value can be relocated. The objects captured by reference being ref-qualified, if they are used as a reloc operand, they will then merely be forwarded.

The following is well-formed:

box<int> ptr;
auto const getPtr = [p = reloc ptr](this auto self reloc)
{
    foo(reloc self.p);
};
(reloc getPtr)();

But this is ill-formed:

box<int> ptr;
auto const getPtr reloc = [p = reloc ptr](this auto self reloc)
//                ^ ill-formed decomposition
{
    foo(reloc self.p);
};
auto ptr2 = reloc getPtr.p;

5.2.8. Implicit decomposition of temporaries

Temporary objects can be implicitly decomposed to allow relocations in the following scenarios (but non exclusively):

struct D : public B {};
D getD();
std::pair<std::string, std::string> getPair();

B b = getD(); /* under conditions, equivalent to:
    auto d reloc = getD(); B b = reloc d.B; */
std::string s = getPair().first; /* under conditions, equivalent to:
    auto pair reloc = getPair(); std::string s = reloc pair.first; */

Inspired by [class.temporary] we add a clause to when a subobject of a temporary is to be converted to a prvalue (for instance because passed to the relocation constructor or relocation assignment operator).

In all the expressions listed in 6, the resulting expression can be converted to a prvalue with implicit decomposition:

  • In 6.3, the C-array case, the array decomposition is always legal and each of its elements are considered as complete objects (their destructor will be implicitly invoked). It’s only if that array element is relocated or further implicitly decomposed that its destructor will not be implicitly invoked (for that element only).

  • In 6.5, the pointer to data member case, the pointer to data member must be constant-evaluated. The language will identify which data member is pointed at. It’s only if that data member is relocated or further implicitly decomposed that its destructor will not be implicitly invoked. The pointer must be constant-evaluated, as it is otherwise impossible to know at compile-time whether it refers to a direct data member or to one of a base class (in which case further implicit decompositions will happen). This information is required at compile-time to assess the well-formedness of the expression. If the pointer is not constant evaluated, then no implicit decomposition can happen.

The implicit decomposition materializes the temporary complete object. Further implicitly decompositions occur for each data member access (or array element access for array-types) or cast to a base class, to extract the desired subobject.

If any implicit decomposition is illegal, then it does not cause the program to be ill-formed, the expression simply cannot be converted to a prvalue (i.e. remains an xvalue). All the incurred decompositions must be legal, as defined below, or else the implicit decomposition is illegal. In particular, if any virtual base is to be decomposed, then the implicit decomposition is illegal.

An implicit decomposition of a temporary object of type T is ill-formed if any of the following conditions is not satisfied:

  • all subobjects of T are accessible. They all need to be since their destructor will be called if not relocated ;

  • all declared special member functions of T are declared either as defaulted or deleted. Note that private access privilege does not allow an implicit decomposition.

For instance:

class T
{
public:
    std::string _pub;
private:
    std::string _priv;
};
class U
{
public:
    std::string _pub[5];
};

T getT();
U getU();

std::pair<std::string, std::string> getPair();


std::string a = getT()._pub; /* implicit-decomposition is ill-formed
    because T has a private member, move constructor is used */
std::string b = getU()._pub[2]; /* implicit-decomposition is well-formed
    std::string's relocation constructor is used; _pub[0] to _pub[4] but _pub[2]
    are destroyed */
std::string c = getPair().second; /* implicit-decomposition is well-formed;
    std::string's relocation constructor is used */

class V
{
public:
    V();
    ~V();
    static std::string GetDefaultName()
    {
        return V()._name; /* implicit-decomposition is ill-formed
            because T has a private member and user-defined special member
            functions. V()._name remains an xvalue.
            Note that this code is valid today, and should
            implicit decomposition be legal in that case (because of the private
            access privilege), then the expression
            would not have the same effect as ~V would not be invoked. */
    }
private:
    std::string _name;

};

As we have seen, decomposition ends the lifetime of the source object. The reader may be concerned that this may break existing ABIs, should the source object be a function parameter passed by value. However we do not foresee any extra breakage other than what the support for the reloc operator does.

Indeed if the decomposed object is not early destructible, then the function may silently relocate its argument to some local storage before the function body is entered. This is a putative workaround and is not part of the proposal. Nonetheless it is made possible in the object decomposition requirements.

5.2.10. Decomposition in constexpr

Object decomposition can be used in constexpr functions and constant-evaluated expressions.

5.2.11. Examples

5.2.11.1. Nominal case

One of the main practical uses of object decomposition is for compound types, such as std::pair. Note that this code would not be feasible without relocation and without decomposition.

void bar(string, box<int>);

void foo(pair<string const, box<int>> p reloc)
{
    bar(reloc p.first, reloc p.second);
}
5.2.11.2. Custom extractor
class T
{

    string const _key;
    box<int> _val;

public:

auto val1 = getT().getVal();

5.3. Ill-formed reuse of relocated objects

5.3.1. Variable state tracking

This section describes the static analysis that is required to prevent reuses of a relocated object.

The reloc operator changes the state of its operand, imposing restrictions of how the variable can be used in the next expressions.

Let us formally introduce the new states a local variable can have:

  • alive (A): this is the default state. As of today in C++, all variables are in this state.

  • relocated (R): the variable was passed as operand to the reloc operator.

  • alive-or-relocated (A-R): the variable may be relocated or alive. For instance the variable will have this state at the end of an if statement, if the variable was relocated in one path and remained alive in the other.

Those states are evaluated at compile-time, and their primary use is to verify the well-formedness of expressions.

The state of a given variable (including function parameters) is evaluated as follows:

  • The variable starts in the A state.

  • The state of the variable is tracked by examining potentially-evaluated expressions, from one expression to the next, following the evaluation order.

    • If two or more expressions have an unspecified evaluation order with one another, then expressions containing a reloc operator with the tracked variable as operand are examined first (in any order).

    • Expressions that are part of unevaluated operands are not examined.

    • Expressions that are part of a discarded statement of a constexpr if statement are not examined.

  • The id-expression designating the tracked variable is ill-formed if the expression is examined and the variable’s state is not A.

    • If the id-expression designates a non-direct subobject of a decomposed object, then its state refers to the state of the direct base that contains it.

    • If the id-expression is used as operand of the reloc operator, then the variable transitions to the R state after the reloc expression examination.

  • If the code path forks (for instance because of an if statement), then all the different code branches need to be examined.

  • If two or more code paths rejoin, then the resulting state of the variable is the OR-combination of the state it had in all the joined code branches.

  • On a code jump:

    • if the code jumps before the variable declaration or after the variable enclosing scope, then the state analysis for this code branch stops here for this variable.

    • otherwise the state of the variable after the jump is the OR-combination of the state it had before the jump, and the state it would have had at the destination code location without taking the jump. If the destination code location cannot be reached without jump, then the jump does not change the state the variable. The state of the variable prior to the jump is memorized for this code jump.

    • if a same code jump needs to be taken an extra time, then the state of the variable is compared to the one previously memorized. If they are identical then the state analysis for this code branch stops here for this variable. Otherwise the new state prior the jump is updated and the jump re-examined.

  • In a try block, if the variable was declared before the block: at the end of an expression that may throw, a code jump to each catch block may be examined. This code jump is necessary:

    • if the state of the variable has changed prior to when the last jumps to the catch blocks were made.

    • or if no last jumps to catch blocks were made, then compare the state the variable had when entering the try block against the current state and perform the jumps if they differ.

  • This state analysis stops until code reaches the natural end of scope of the variable.

NOTE: We don’t expect this analysis to be costly. It is only necessary in functions for the variables that are relocated. If there are none, then this analysis is not needed.

5.3.2. reloc in unevaluated operands

The reloc operator can be used in unevaluated operands. Such expressions are ignored by the code analysis described above. If reloc is used in an unevaluated operands, then (a) their operands are always considered to have the alive state, and (b) the state of their operands do not change.

For instance:

void foo(T x)
{
    decltype(reloc x) y = reloc x; // well-formed
    decltype(reloc x, (reloc x).m) z = y.m; // well-formed
}

5.3.3. Examples

Consider the following examples:

void reloc_showcase_01()
{
    const T var = getT();
    bar(reloc var);
    if (sometest(var)) // ill-formed: state of 'var' is relocated
        do_smth(var); // ill-formed: state of 'var' is relocated
}

var cannot be reused after the reloc call.

void reloc_showcase_02()
{
    const T var;
    {
        const T var;
        bar(reloc var);
        do_smth(var); // #1 ill-formed: state of 'var' is relocated
        {
            const T var;
            do_smth(var); // OK
        }
        do_smth(var); // #2 ill-formed: state of 'var' is relocated
    }
    do_smth(var); // OK
}

At #1 and #2, the calls to do_smth(var) are allowed because the name var does not resolve to the relocated object.

void reloc_showcase_03()
{
    const T var = getT();
    if (sometest(var))
        bar(reloc var); // #1, var state is relocated
    else
        do_smth(var); // #2, var state is alive
    // var state is alive-or-relocated
}

At #2 do_smth(var) is allowed because var state is not affected by the reloc call at #1 (they occur in different code branches).

void reloc_showcase_04()
{
    const T var = getT();
    if (sometest(var))
        bar(reloc var); // #1
    else
        do_smth(var); // OK
    // [...]
    do_smth_else(var); // #2, ill-formed: state of 'var' is A-R
}

At #2, do_smth_else(var) is an error because var is mentioned after the reloc call at #1.

void reloc_showcase_05()
{
    const T var = getT();
    if (sometest(var))
        bar(reloc var);
    else
        do_smth(reloc var); // OK
    // var state is relocated
}

Both reloc are okay as they happen on different code paths.

void reloc_showcase_06()
{
    const T var = getT();
    bool relocated = false;
    if (sometest(var))
    {
        bar(reloc var);
        relocated = true;
    }
    else
        do_smth(var); // OK
    // [...]
    if (!relocated)
        do_smth_else(var); // ill-formed: state of 'var' is A-R
}

It does not matter that the developer tried to do the safe thing with the relocated variable. The code-path analysis disregards run-time values and explores all branches of an if statement.

void reloc_showcase_07()
{
    constexpr bool relocated_v = my_can_relocate<T>{}();
    const T var = getT();
    if constexpr(relocated_v)
    {
        bar(reloc var);
    }
    else
        do_smth(var); // OK
    // [...]
    // var state is R if relocated_v is true, A otherwise
    if constexpr(!relocated_v)
        do_smth_else(var); // OK
}

The above example is safe because of the use of if constexpr.

void reloc_showcase_08()
{
    const T var = getT();
    if (sometest(var))
    {
        bar(reloc var);
        return;
    }
    do_smth(var); // OK
}

This example is also safe thanks to the return statement right after the reloc instruction, which prevents from running do_smth(var);.

void reloc_showcase_09()
{
    const T var = getT();
    for (int i = 0; i != 10; ++i)
        do_smth(reloc var); // ill-formed: state of 'var' is A-R (on second iteration)
}

This is ill-formed as each iteration reuses var which is declared before the loop body.

In the code path analysis:

  1. At the first loop iteration, the variable gains the relocated state.

  2. The loop increment is examined, and it does not change the state of var.

  3. The loop condition is examined, and it does not change the state of var.

  4. The code jump is examined for the first time, memorizing the state of var at that moment (relocated).

  5. The new state of var is now A-R.

  6. do_smth(reloc var) is examined, and reloc var is ill-formed as var is not in the alive state.

void reloc_showcase_10()
{
    const T var = getT();
    for (int i = 0; i != 10; ++i)
    {
        if (i == 9)
            do_smth(reloc var); // ill-formed: state of 'var' is A-R (on second iteration)
        else
            do_smth(var); // ill-formed: state of 'var' is A-R (on second iteration)
    }
}

This is ill-formed for the same reason as above.

void reloc_showcase_11()
{
    const T var = getT();
    for (int i = 0; i != 10; ++i)
    {
        if (i == 9) {
            do_smth(reloc var); // OK, var state is relocated
            break;
        }
        else
            do_smth(var); // OK, var state is alive
    }
    // var state is A-R
}

Adding the break statement right after the reloc call makes the code snippet well-formed. Indeed the break statement forces the loop exit, which implies that the conditional jump at the end of loop (that may start the next iteration) is no longer part of the code path that follows the reloc instruction.

void reloc_showcase_12()
{
    for (int i = 0; i != 10; ++i)
    {
        const T var = getT();
        do_smth(reloc var); // OK
    }
}

var is local to the for-loop body, so reloc is well-formed here. The code path analysis for this variable does not require several loop iterations, as the variable scope ends before the code jump leading to the next iteration is evaluated.

void reloc_showcase_13()
{
    const T var = getT();
from: // #1
    if (sometest(var)) // #2, ill-formed: var state is A-R after the jump
    {
        do_smth(var); // #3, ill-formed: var state is A-R after the jump
        return;
    }
    else
    {
        do_smth(reloc var); // #4, ill-formed: var state is A-R after the jump
    }
    // #5
    goto from;
}

Because of #4, the state of var at #5 is R. The goto statement is executed and we are back at #1. var state is then the OR combination of the A state and the R state, which is A-R. Then the expressions #2, #3 and #4 are ill-formed because var is not in the A state.

void reloc_showcase_14()
{
    const T var = getT();
from:
    if (sometest(var)) // var state is alive
    {
        do_smth(var); // var state is alive
        goto from;
    }
    else
    {
        do_smth(reloc var);
    }
}

In this scenario goto is placed in a way that does not trigger the reuse of relocated var.

void reloc_showcase_15()
{
    union { T x; U y; };
    x = getT();
    if (sometest(x))
    {
        do_smth(reloc x);
        x = getT(); // well-formed
    }
    else
    {
        reloc x; // destroy x
        y = getU();
        do_smth_else(reloc y); // well-formed
        x = getT(); // well-formed
    }
    do_smth_else(reloc y); // well-formed
}

reloc does not prevent from reusing the names of anonymous union members.

void reloc_showcase_16()
{
    T x;
    if (sometest(x))
    {
        do_smth(reloc x);
    }
    else
    {
        auto const y reloc = reloc x;
        do_smth_else(reloc y.m); // well-formed
        // equivalent to: do_smth_else((reloc x).m);
    }
    do_another_thing(x); // ill-formed: state is now R
}

do_another_thing(x) is ill-formed as x is relocated.

void reloc_showcase_17()
{
    T x;
    if (sometest(x) || sometest(reloc x)) // well-formed: x state is A-R
    {
        do_smth(x); // ill-formed: x state is A-R
    }
    else if (othertest(x)) // ill-formed: x state is A-R
    {
        foo();
    }
}

void reloc_showcase_18()
{
    // unspecified evaluation order
    { T x; auto y = reloc x + reloc x; } // ill-formed
    { T x; auto y = x + reloc x; } // ill-formed
    { T x; auto y = reloc x + x; } // ill-formed
    { T x; auto y = x[reloc x]; } // ill-formed

    // sequenced evaluation order
    { T x; auto y = x, reloc x; } // well-formed
    { T x; auto y = reloc x, x; } // ill-formed
    { T x; auto y = x or reloc x; } // well-formed
    { T x; auto y = reloc x or x; } // ill-formed

    // unspecified evaluation order with ternary
    { T x; foo(x, reloc x); } // ill-formed
    { T x; foo(x, test() ? reloc x : x); } // ill-formed
    { T x; foo(test() ? reloc x : x); } // well-formed
}

If two or more expressions have an unspecified evaluation order, then to determine their well-formedness we examine the expressions containing reloc first, and examine the rest after (in any order).

void reloc_showcase_19()
{
    T x = getT();
    try
    {
        foo();
        bar(reloc x);
    }
    catch (std::exception const& excp)
    {
        std::cerr << excp.what() << " for " << x << std::endl;

    }
}

5.3.4. Conditional destruction

NOTE: This section only applies to variables that are not ref-qualified.

The variable state analysis described here may be used to know what kind of cleanup is necessary at scope exit (i.e. if the end of scope is reached or an exception is emitted).

When this happens, if the variable is in A-R state, and that its type is not trivial, then implementations must track at runtime the actual state of the variable (A or R) and process its destruction accordingly:

  • If the variable was the operand in an evaluated reloc expression, then the variable may need to be destructed following the rules described here.

  • Otherwise the variable must be destructed by its destructor following normal rules.

NOTE: If the variable was the operand of a reloc expression, but that expression was not evaluated, then its lifetime is not affected and the variable must still be destroyed normally.

How this runtime tracking is done is implementation-defined, although it will probably take the form of extra flags in the function stack.

For instance:

void foo()
{
    T obj = /* ... */;
    if (some_test())
        bar(reloc obj); // obj state is relocated
    else
        handle_error(); // obj state is alive
    live_on(); // obj state is alive-or-relocated
}

After the call to live_on(), or should live_on throw, obj destructor is only implicitly invoked if reloc obj was not evaluated. Implementations may simply turn on a flag right before the evaluation of the reloc expression.

Concerns have been expressed that extra flags would violate the "don’t pay for what you don’t use" principle. We acknowledge this concern, but feel that the user is getting at least something out of this. Alternatives would be for the source object to be destroyed implicitly at the opening or closing brace of the else, for the code to be ill-formed unless the source object is relocated within the else, or for the code to be ill-formed unconditionally. Note that in each of these cases, the user can recover our preferred behavior in library, using std::optional to add the tracking flags that in our proposal would be provided by the language.

5.4. Relocation constructor

Now that we have introduced the reloc operator and object decomposition, we introduce the relocation constructor, which is built upon those new concepts. As relocation happens from prvalues, the constructor takes a prvalue as parameter. The relocation constructor must also relocate the resources of the source object and will rely on object decomposition for that purpose. Its signature logically follows: T(T reloc).

This signature was picked as it completes the C++ tripartite value system. The copy constructor creates a new instance from an lvalue, the move constructor from an xvalue, and then the relocation constructor from a prvalue.

Note: a further benefit of this syntax is that it is currently ill-formed [class.copy.ctor]/5, and thus available for extension.

A point of confusion may be that the syntax implies an infinite regress: the parameter must be constructed, which requires a prior call to the relocation constructor, and so on. This is not the case; if the source object was previously the operand of the reloc operator, it was transformed into a prvalue immediately before entering the relocation constructor, and the parameter of the relocation constructor is that same prvalue. (If the source object was already a prvalue, there is no issue; the parameter is that prvalue.)

An attractive intuition is that the parameter aliases the source object in the same way as a reference or a structured binding declaration. However, this is misleading; the lifetime of a source object glvalue has already ended and so use of a pointer or reference referring to the source object has undefined behavior, except as provided by [basic.life] and [class.cdtor].

Note: this behavior matches that for the destructor of a class type; see [basic.life] paragraph 1.

This intuition is only useful in so far as the ABI for a relocation constructor prvalue parameter is likely to be the same as that for a copy or move constructor parameter, since the prvalue parameter may have the same storage location as a previously existing glvalue.

Note: it does not matter that the ABI for the relocation constructor parameter differs from that for a prvalue parameter in normal functions, since it is not possible to take the address of a constructor.

The role of the relocation constructor is to construct a new instance by destructively stealing the resources from the source object. Unlike the move constructor, the relocation constructor needs not to leave the source object in valid state.

5.4.1. Declaration

The relocation constructor can be declared (implicitly or explicitly), defaulted and deleted like any other constructor.

The relocation constructor must take a decomposed source object of same type (modulo cv-qualifiers) as first parameter. Extra, defaulted parameters are authorized. Hence its signature must be T(T cv src reloc, [...]), with cv the cv-qualifiers of src. In particular, the signature T(T) (without reloc) remains illegal as of today.

A class-type that provides a relocation constructor has some impact on the program ABI. See the ABI section.

5.4.1.1. Implicit declaration

If no user-defined relocation constructors are provided for a class-type T, and all of the following is true:

  • there are no user-declared copy constructors ;

  • there are no user-declared copy assignment operators ;

  • there are no user-declared move constructors ;

  • there are no user-declared move assignment operators ;

  • there are no user-declared relocation assignment operators ;

  • there is no user-declared destructor ;

  • there are no base class of T which has a virtual destructor but no virtual slicing function.

Then the compiler will declare a relocation constructor as a non-explicit inline public member of its class with the signature T::T(T reloc).

5.4.1.2. Deleted implicitly-declared or defaulted relocation constructor

The implicitly-declared or defaulted relocation constructor for class T is defined as deleted:

  • if T has subobjects that explicitly declare a deleted relocation constructor ;

  • or T has subobjects with missing relocation and move constructors (i.e. that are deleted, inaccessible, or ambiguous).

  • or T has subobjects with deleted or unaccessible destructor.

As for move constructors, a defaulted relocation constructor that is deleted is ignored by overload resolution.

Note: this means that a class with an explictly deleted relocation constructor will still be relocated if necessary, but through the move (or copy) constructor and destructor.

5.4.1.3. Exception specification

Although it is not advised, the relocation constructor is allowed to terminate by throwing an exception (just like the destructor). As for any other function, a noexcept specification can be specified on the relocation constructor.

A relocation constructor that is implicitly declared or defaulted on its first declaration has a noexcept(true) noexcept specification unless any constructor or destructor of a subobject that the default definition would call is potentially-throwing.

A non-defaulted user-declared relocation constructor with unspecified noexcept specification is potentially-throwing.

5.4.1.4. Trivial relocation

A class-type that has virtual bases or is polymorphic cannot be trivially relocatable, because of how those features are sometimes implemented.

About virtual inheritance: A common implementation for virtual inheritance is to store in the memory layout of the derived class a pointer to the virtual base. This is incompatible with trivial relocation as the pointer needs then to be adjusted to the new memory location. Another possible implementation would be to store an offset to the virtual base location, which would make it trivially relocatable.

About polymorphic types: You might think that polymorphic types can be trivially relocatable, as they only contain a pointer to a virtual table. However this is not true on some implementations. Quoting [D3780R0]’s explanation:

[...] On some architectures/ABIs (such as arm64e) these [vtable] pointers are authenticated, meaning that some bits of the pointer value are used to store a cryptographic signature. This signature gets verified when one accesses the virtual table pointer (for instance by calling a virtual function).

One of the inputs of the signature is target address of the pointer (that is, the address of the virtual table). Another input, which is crucial to this story, is the address of the virtual table pointer itself.

This means that, on those architectures, relocating a polymorphic object by using a simple byte copy would produce an object whose virtual table pointer would fail to authenticate.

As a consequence, a relocation constructor of a class type T is trivial if it is not user-provided and if:

  • T has no virtual base classes, and

  • T is not a polymorphic type, and

  • for each direct base class and direct non-static data member of class type or array thereof, the relocation operation (which may be a relocation constructor or synthesized from copy/move constructor plus destructor) selected to relocate that base or member is trivial.

Note that implementations are allowed to benefit from the trivial relocation optimization (i.e. identical to a memcpy call) if the class-type is not trivially relocatable because of virtual inheritance or polymorphism (should their implementation of such class traits be compatible with trivial relocation).

C++26 defines trivial relocatability. We amend this definition to account for the relocation constructor. A trivially relocatable class is one which:

  • has a trivial, eligible relocation constructor, or ;

  • does not have a relocation constructor (including one that is deleted), and is trivially relocatable according to C++26.

Note: eligible is defined in [special].

Scalar types, trivially relocatable class types, and arrays and cv-qualified versions thereof are trivially relocatable.

We also tighten the definition of "trivial class" (and thus "trivial") to require that the class in question be trivially relocatable as well as trivially copyable. This is to ensure that if the user wants code to be called on relocation, the library does not bypass said code by, say, using memmove.

5.4.1.5. Interaction with C++26 memberwise_trivially_relocatable

This proposal provides its own way to define trivial relocation, while C++26 also provides the memberwise_trivially_relocatable trait. We do not see it as a blocking point:

  • memberwise_trivially_relocatable can be specified by mistake causing undefined behaviors. On the other hand, having the trivial relocation trait deduced by whether the relocation constructor is trivial is a safer approach, which does not make room for human errors ;

  • memberwise_trivially_relocatable only affects objects that live in dynamic storage, while the relocation constructor is also available for objects with automatic storage. They answer different needs.

We propose memberwise_trivially_relocatable to have no effect if the class-type declares a user-provided relocation constructor (i.e. the constructor is declared and not defaulted). Under this condition, the class-type cannot be considered as trivially relocatable.

This behavior follows the existing logic memberwise_trivially_relocatable has with regards to virtual bases: it’s not an error if the two are combined, memberwise_trivially_relocatable is merely ignored.

Note that memberwise_trivially_relocatable is not equivalent to defining a defaulted relocation constructor, as the latter will have an impact on the ABI. Hence in the following snippet:

struc T memberwise_trivially_relocatable
{
    T(T const&);
    T(T&&);
};
void foo(T x)
{
    sink(reloc x); // #1
}

Whether relocation happens at #1 depends on the implementation, that is on whether x is early destructible. If relocation happens, then x can be trivially relocated, as if by memcpy.

If this proposal is accepted, we expect memberwise_trivially_relocatable to vanish over time in favor of the more natural relocation constructor default declaration.

5.4.2. Definition

5.4.2.1. Decomposition of the source object

As its signature suggests, the relocation constructor decomposes its source object. Refer to the above section to see how decomposition unrolls.

5.4.2.2. Virtual bases

Virtual bases have a special treatment in constructors and destructors: they are only contructed and destructed by the class-type of the complete object, and not by its base classes. The relocation constructor has the same behavior. Hence it must be passed with the same extra information that is passed today to any constructor and to the destructor: (a) whether it is in charge of the construction of the virtual bases, and (b) whether it is in charge of the destructon of the virtual bases of the source object.

It follows that the relocation constructor will construct the virtual bases of the target object (respectively destroy them from the source object) only if the extra information (a) (respectively (b)) states so.

For instance:

class B
{
    B(B src reloc);
    // [...]
};
class C : public virtual B
{
    C(C src reloc);
    // [...]
};
class D : public C
{
    D(D src reloc);
    // [...]
};

void foo(C);

void bar()
{
    D const d reloc = getD();
    foo(reloc d.C); // #1
}

Here, at #1 when bar calls the C’s relocation constructor to build the parameter of foo:

  • C(C) is in charge of constructing the virtual base B ;

  • C(C) is not in charge of destroying the virtual base B of its parameter. src.~B() is not called by the relocation constructor ;

  • The default implementation of C(C) will move-construct the virtual base ;

  • foo gets a C object owning its virtual base.

After #1:

  • d.B still points to valid data, albeit that it was likely moved-from in C(C) ;

  • d.B destructor will be implicitly invoked, as it will be for all the data members of d.D ;

5.4.2.3. Default definition

The default relocation constructor implementation for a class-type T depends on T’s type traits.

If T is trivially relocatable then the relocation constructor effectively (ignoring padding) performs a memcpy over its entire memory layout.

Otherwise the constructor implementation first decomposes the source object, and then performs memberwise relocations. In the relocation constructor T(T src reloc), for each subobject s (of type S) of T, in declaration order:

  • if S is a virtual base, then S is move-or-copy-constructed as if by: S{std::move(src.S)} ;

  • otherwise we construct s (or S for direct base classes) by calling its own relocation, move or copy constructor, as if by: s{reloc src.s} (or S{reloc src.S});

5.4.2.4. User-provided definition

Although the default definition should cover almost all cases, users can provide their own definition of the relocation constructor. Doing so is relatively straightforward thanks to the object decomposition feature. The only reason we have found to write a custom relocation constructor is to adjust some self-referencing pointers, otherwise the default implementation should suffice.

Consider the following examples:

struct T
{
    std::string _a, _b, _c;

    // Dummy example to explain all the steps of the relocation constructor.
    T(T src reloc) :
        _a{std::move(src._a)}, _c{reloc src._c} {} /*
        1. T::_a is constructed using the move constructor.
        2. T::_b is default constructed.
        3. T::_c is constructed using std::string's relocation
           constructor, from src._c.
        4. src._b and src._a are destructed (in that order)
           when the constructor body exits.
    */
};

struct U
{
    std::string _a;

    ~U();

    // Second dummy example.
    U(U src reloc) {} /*
        1. U::_a is default-constructed.
        2. src._a is destructed.
    */
};

// Motivating example
template <class T>
class BinaryTree
{
public:
    // works also if T is relocate-only
    BinaryTree(BinaryTree src reloc) noexcept : _root{reloc src._root}
    {
        /* fixup references */
        if (_root._left)
            _root._left->_parent = &_root;
        if (_root._right)
            _root._right->_parent = &_root;
    }
private:
    struct BTNode {
        BTNode* _parent = nullptr;
        BTNode* _left   = nullptr;
        BTNode* _right  = nullptr;
        T _value;
    };
    BTNode _root;
};
5.4.2.5. Delegating relocation constructor

We do not support writing a delegating relocation constructor. This is hardly possible because of the decomposition of the source object.

We do not consider this as a blocking issue. Additional default parameters are supported with the relocation constructor. And constructor delegation may still happen with an extra layer:

class T
{
    struct Impl
    {
        // [...] all data members useful to T go there instead.
    };

public:
    T(T src reloc) : T{reloc src._impl, {}} {}
    //                ^ delegating constructor

private:
    T(Impl src, Helper h) : _impl{reloc src} {}

    Impl _impl;

};
5.4.2.6. Additional parameters

As with copy and move constructors, it is permissible to add additional parameters to a relocation constructor, on condition they have a default initializer.

One case where this can be of use is if the user needs space to store information and/or resources for the duration of the relocation constructor, for a contrived example:

class T
{
public:
    class Helper {
    public:
        Helper() = default;
        ~Helper() { delete p; }
    private:
        friend T;
        int* p;
    };

    T(T src reloc, Helper storage = {}) noexcept(false)
        : _p(storage.p = std::exchange(src._p, nullptr))
        , _q{reloc src._q}
        , _r{reloc src._r}
    {
        storage.p = nullptr;
    }

    ~T() {
        delete _p;
    }

private:
    int* _p;
    RelocateOnly _q;
    ThrowingRelocate _r;
};

In the above, T::_p does not manage its own lifetime, but the presence of T::_r means that T::T(T reloc) is not noexcept so we need to release its resources if an exception is thrown during relocation.

5.4.3. Invocation

The relocation constructor is invoked as necessary to relocate a prvalue from one storage location to another. Use of the reloc operator does not guarantee that a relocation constructor (if present) will be called, since it may be elided if the compiler can arrange that the source glvalue was constructed at the appropriate address.

In particular, code of the form auto x = reloc y; is highly likely to be a no-op, simply renaming an existing object. This is however likely to find use for "sealing" objects with complex initialization, replacing the idiom of immediately-invoked function expressions (IIFEs, [IIFE]):

Before After 
T const x = std::invoke([&]
{
    T x;
    x.modify(y, z);
    return x;
});

T x_mut;
x_mut.modify(y, z);
T const x = reloc x_mut;

Or, consider:

C f(int i) {
    C c1, c2;
    if (i == 0)
        [[likely]] return reloc c1;  // #1
    else if (i == 1)
        [[likely]] return c1;  // #2
    else
        [[unlikely]] return c2;  // #3
}

At #1 the reloc is largely redundant; the end-of-life optimization means the compiler is entitled to treat c1 as a prvalue anyway, as in #2. Indeed, the likelihood annotation encourages the compiler to construct c1 in the return slot, such that both #1 and #2 are a no-op. It is only #3 that is likely to invoke the relocation constructor.

5.4.4. Virtual slicing function

Although relocation and polymorphism are unlikely to be mixed together, there are still situations where it may happen. Consider the following scenario:

class D : public B { std::string _str; };

B* b = new D;

B sliced = std::reloc_and_reclaim(b);
// reloc_and_reclaim relocates the given address to
// its return value and deallocates the memory.

The proposed relocation design must ensure this will not to cause any object slicing. In order to address this loophole, we propose a new virtual slicing function. std::reloc_and_uninitialize and std::reloc_and_reclaim must then use it, if present, to prevent object slicing.

5.4.4.1. Declaration

A class-type that explicitly declares a relocation constructor and has a virtual destructor, then implicitly declares a virtual slicing function, with the same access specifier as that of the destructor:

  • The relocation constructor must be explicitly declared and not deleted.

  • The virtual destructor may be declared in the class-type, or inherited from a base class.

If a class-type inherits from a base type that provides a virtual slicing function, then it also triggers the declaration of the slicing function with the same access specifier as that of the destructor.

The virtual slicing function cannot be user-declared and cannot be invoked by the user. It acts as a hidden virtual function that makes the link between the relocation world and the polymorphism world.

struct Type1 {}; //< no virtual slicing function

struct Type2
{
    Type2(Type2 const&) = default;
    Type2(Type2&&) = default;
    Type2(Type2 reloc) = default;
    ~Type2() = default;
    // no virtual slicing function
};

struct Type3
{
    virtual ~Type3() = default;
    // no virtual slicing function, relocation constructor is not implicitly declared
    // because of the destructor declaration
};

struct Type4
{
    Type4(Type4 reloc) = default;
    virtual ~Type4() = default;
    // declares a virtual slicing function
};

struct Type5 : public Type3
{
    // no virtual slicing function.
    // the relocation constructor is not implicitly declared,
    // as the inherited virtual destructor prevents its implicit declaration
};

struct Type6 : public Type3
{
    Type6(Type6 reloc) = default;
    // declares a virtual slicing function
};

struct Type7
{
    Type7(Type7 reloc) = default;
    // no virtual slicing function because no virtual destructor
};

struct Type8 : public Type7
{
    virtual ~Type8() = default;
    // no virtual slicing function because no explicit relocation constructor
    // (relocation constructor is not implicitly declared)
};

struct Type9 : public Type8
{
    Type9(Type9 reloc) = default;
    // declares a virtual slicing function
};

As you can see, the ABI break introduced by the new virtual function can only be opt-in: if no relocation constructor is explicitly declared, then there are no ABI breaks. See also the discussion about the virtual slicing function.

5.4.4.2. Definition

Let T be a class-type with a virtual slicing function. The aim of the slicing function is to decompose T, destroy all the unwanted parts but the desired base class, and to relocate that base class to a new storage space.

The parameters of the slicing function are implementation-defined. At minimum there must be:

  • the object to slice, which is the this parameter ;

  • the target type of the object to construct, which we will call U. U is by construction, either T or a (maybe non-direct) base class of T which provides a slicing function. U may be a template parameter (in which case the slicing function is a template function, possibly causing multiple vtable entries), or a type information supplied at run-time.

  • the address where it is to be constructed, which we will call u.

The slicing function handles the destruction of its this object. Upon exit (normally or through an exception), the this object is destroyed.

A possible implementation of the virtual slicing function is:

  1. If U is the same as T, then relocates this to u. This is done by invoking the relocation constructor, move constructor or copy constructor. If the relocation constructor was not invoked, then the destructor of this must be invoked.

  2. Otherwise let V be the direct base of T which is on the inheritance path from T to U (V may be U):

    1. Decompose this. Then recursively invoke the V’s slicing function on V subobject, forwarding the U and u parameters.

    2. Upon exit, the destructors of all non-relocated subobjects of src are implicitly invoked.

The slicing function is defined in the same translation units of the destructors. If the destructor is inline, then so is the slicing function.

5.4.4.3. Ill-fomed definition

A virtual slicing function definition of a class-type T is ill-formed if:

  • the destructor of T is user-provided ;

  • or T has no eligible relocation, move and copy constructor ;

  • or T has no eligible destructor and relocation constructor ;

  • or any of the direct base of T, which declares a virtual slicing function, has a non-accessible slicing function ;

  • or if any of the subobject of T has an inaccessible destructor.

All points but the first merely ensure that all the functions which the slicing function may call are invocable from that context.

Note that if the destructor of T is user-provided, then because the slicing function proceeds by successive object decompositions and subobject destructions, T’s destructor may not be called (it is called in the case the source and target types are the same, and that type does not provide an eligible relocation constructor). This may result in some unwanted behavior such as:

struct B
{
    B(B reloc) = default;
    virtual ~B() = default; //< triggers virtual slicing function declaration
};
struct D : public B
{
public:
    D() : _ptr{new T} {}
    ~D() override { delete _ptr; }
private:
    T* _ptr;
};

The slicing function that slices a D object to B would decompose its source D object, hence bypassing the call to D’s destructor ... causing a memory leak. This is why the slicing function definition is ill-formed if the destructor is user-provided.

A possible fixup to the above example is to wrap _ptr to an RAII object, such as std::unique_ptr. Then the destructor can be defaulted, and the slicing function will call the unique_ptr’s destructor.

5.5. Relocation assignment operator

We further introduce the relocation assignment operator. Its signature shall be: T& T::operator=(T [reloc]), the parameter decomposition being optional. If the parameter is decomposed, the function is then called the decomposing relocation assignment operator. Such non-decomposing operators may already be defined in existing codebases, but the proposed changes will not interfere with them.

Sometimes we also make mentions to the prvalue-assignment operator. It refers to the same function, but further indicates that this function existed prior to the proposal.

5.5.1. Declaration

The relocation assignment operator becomes a special member function. As such, declaring one breaks the Rule of Zero, which was not the case previously. A user-declared relocation assignment operator will prevent an implicit declaration of the relocation constructor.

The relocation assignment operator may be implicitly declared, and may be defaulted or deleted.

Only the decomposing version may be defaulted (T::operator=(T) = default; is an ill-formed definition).

5.5.1.1. Implicit declaration

If a class-type follows the Rule of Zero, then the compiler will declare an inline public decomposing relocation assignment operator.

5.5.1.2. Deleted implicitly-declared or defaulted relocation assignment operator

The implicitly-declared or defaulted relocation assignment operator for class T is defined as deleted:

  • if T has subobjects that have an implicitly or explicitly deleted relocation assignment operator ;

  • or T has subobjects that have inaccessible relocation, move or copy assignment operators ;

  • or T has subobjects with deleted or unaccessible destructor.

A defaulted relocation assignment operator that is deleted is ignored by overload resolution.

5.5.2. Relocation assignment operator parameter relocation elision

As with the relocation constructor, it is desirable that the parameter should be the source object converted to a prvalue, and not a temporary prvalue relocated from the source object. This is particularly critical for the default definition of the operator, which (as you might suspect) performs memberwise calls to other relocation assignment operators. Without elision, that would imply recursive relocation of each subobject, down to their smallest unbreakable parts (incurring O(N2) byte copies, N being the size in bytes of the source object).

However, this poses a problem since it is possible to take the address of a relocation assignment operator, yielding a pointer (or reference) with (typical) signature T& (T::)(T), implying that the source object must occupy a parameter slot, which may not find it possible to have the same storage address as the source object, and/or which the caller may expect to destroy (see § 7.1 Potential ABI changes).

Nevertheless, we mandate elision if the class-type (possibly implicitly) declares a non-deleted relocation constructor, or a decomposing relocation assignment operator (possibly defaulted). The proposed elision is performed in such a way as to avoid ABI break (more on that on the ABI section).

If elision is mandated, then the assignment operator declaration actually declares two member functions:

  • the non-eliding one, which takes its input parameter by value. If no optimizations allow otherwise, this is the function that will be invoked when user-code calls the assignment operator. It is the prvalue-assignment operator as we know it today ;

  • the eliding one, which takes its input parameter as if by reference, and has the same return type as the non-eliding one. The eliding function has no identifier and does not participate in overload resolution. Users cannot take its address. The eliding operator is forced to have callee-destroy ABI: the operator is in charge of the lifetime of the source object.

The definition of the assignment operator (which is user-provided or defaulted) will serve as the definition of the eliding operator.

The non-eliding operator definition is generated by the compiler, and merely wraps the call to the eliding one:

  • If the source object passed to the non-eliding operator is early destructible, then the operator:

    1. Calls the eliding operator, passing the source object as if by reference.

    2. It forwards as return value whatever the eliding operator returns.

  • Otherwise then the operator:

    1. Creates a local copy of the source object, using move or copy constructor.

    2. Calls the eliding operator, passing that copy by reference.

    3. It forwards as return value whatever the eliding operator returns.

    4. It does not call the destructor of that local copy.

NOTE: If the implementation can guarantee that the relocation assignment operator parameter is passed by address and is early destructible, then the non-eliding version is not needed.

If the address of the assignment operator is queried, then the address of the non-eliding version is returned. If the assignment operator is virtual, then only the non-eliding version is considered to be virtual and is added to the vtable entry.

5.5.3. Definition

5.5.3.1. Default definition

As you would expect, the default definition merely delegates to the relocation assignment operator of all its subobjects. In T’s default assignment operator, the source object src of type T is decomposed, and for all its subobjects s of type S:

  • if S is a virtual base, then S is move-or-copy-assigned as if by: static_cast<S&>(*this) = std::move(src.S); ;

  • otherwise we construct s (or S) by calling its own relocation, move or copy assignment operator, as if by: s = reloc src.s; (or static_cast<S&>(*this) = reloc src.S; for base classes);

Thanks to the relocation-assignment operator special eliding, no copies or relocations of the source subobjects are performed.

Also note that this implementation has a strong exception safety, which guarantees to leave the object in a valid state if left by throwning an exception.

5.5.3.2. Possible user definitions

The default definition is enough if the class destructor is also defaulted. If the destructor body performs some resource management (meaning that the resource management is not handled by a subobject’s destructor) then the same kind of resource management is likely expected to take place in the relocation assignment operator, requiring a user-provided implementation.

This section enumerates some notable implementations.

destroy-and-construct

One may be tempted by the infamous destroy-and-construct idiom. It is both convenient (no need to duplicate destructor code and write relocation code for each subobject) and efficient on paper. But if not used with caution, it can lead to serious undefined behaviors (likely program crashes).

T& T::operator=(T src) noexcept
{
    std::destroy_at(this);
    return *std::construct_at(this, reloc src);
}

This function has a poor exception-safety. Should any of the destructor or the relocation constructor throws, the function would exit leaving this in a destructed state (uninitialized memory)... hence the noexcept.

An exception-safe version is possible, requiring more work:

T& T::operator=(T src) requires std::is_default_constructible_v<T>
{
    std::experimental::scope_fail _{[this] { new (this) T; }};
    std::destroy_at(this);
    return *std::construct_at(this, reloc src);
}

Despite the improved exception safety, this pattern is still dangerous when mixed with inheritance. Consider the following code:

struct B
{
    virtual ~B() = default;
    B& operator=(B src); //< using destroy-and-construct idiom
};
struct D : B { std::string _str; };

foo(B& obj) { obj = B{}; }

void bar()
{
    D obj;
    foo(obj);
    // obj._str is now destructed and obj runtime-type info points to B's!
}

destroy-and-construct is only safe with a non-throwing destructor and relocation constructor, and for non-polymorphic types. This implementation is not recommended.

relocate-and-swap

T& T::operator=(T src)
{
    using std::swap;
    swap(*this, src);
    return *this;
}

This implementation has two advantages: it delegates the resource cleanup of this to the destructor of src (no duplicate code) and is exception-safe. Note however that it is not the most efficient approach.

Cleanup and memberwise relocation

T& T::operator=(T src)
{
    cleanup();
    auto src_d reloc = reloc src; // inplace decomposition
    static_cast<B&>(*this) = reloc src_d.B; // relocate base
    this->_a = reloc src_d._a;
    return *this;
}

This implementation is preferred over the other two suggested above. cleanup will perform the resource management performed in the destructor body (if the destructor is defaulted, then so should be the relocation assignment operator).

Note that the decomposition of the source parameter happens after cleanup. If cleanup terminates by throwing an exception, then src must be destroyed (its own cleanup must be called by its destructor). Had it been decomposed from the start, its destructor call would have been bypassed, causing a memory leak in the exception scenario.

Alternatively, a simpler version is possible, should we not want to be bothered by exceptions:

T& T::operator=(T src reloc) noexcept
{
    cleanup();
    static_cast<B&>(*this) = reloc src.B; // relocate base
    this->_a = reloc src._a;
    return *this;
}

Putative std::unique_ptr implementation

Let’s illustrate the cleanup and memberwise relocation pattern by a concrete case. This section discusses the possible implementations of the relocation assignment operator for unique_ptr.

The simpler implementation is:

unique_ptr<T,D>& unique_ptr<T,D>::operator=(unique_ptr<T,D> rhs reloc) noexcept
{
    reset();
    _deleter = reloc rhs._deleter;
    _ptr = rhs._ptr;
    return *this;
}

The implementation is straightforward, we simply deallocate the resources and perform memberwise relocations. The decomposition of rhs ensures its destructor is not run. This implementation assumes that the deleter object is nothrow relocatable.

Note that, had reset() been allowed to throw (reset() is noexcept), the implementation would have been slightly more evolved:

unique_ptr<T,D>& unique_ptr<T,D>::operator=(unique_ptr<T,D> rhs)
{
    reset(); //< can throw, then rhs destructor is called
    auto rhs_members reloc = reloc rhs;
    _deleter = reloc rhs_members._deleter;
    _ptr = rhs_members._ptr;
    return *this;
}

In this version, the decomposition happens at a later stage (note that the relocation caused by the decomposition will be elided). This is to ensure that any exception thrown in the resource destruction sequence (reset()) will trigger the proper destruction of rhs.

relocate-and-exchange

T T::exchange(T new_value);

T& T::operator=(T src)
{
    exchange(reloc src);
    return *this;
}

This implementation relies on an exchange function that sets the object to a new value (src) and returns its former value. Note that such a function is encouraged to be implemented in all relocate-only types.

This implementation is preferred over the relocate-and-swap pattern. It benefits from the same advantages and has less relocation operations involved than what’s needed for a swap.

Putative std::box implementation

Likewise, let’s see a concrete implementation of relocate-and-exchange pattern with std::box. For this section, let’s consider a more realistic std:box<T,A> with an allocator object.

A simple implementation will only need the cleanup and memberwise relocation pattern:

box<T,A>& box<T,A>::operator=(box<T,A> rhs reloc) noexcept
{
    _alloc.deallocate(_ptr);
    _alloc = reloc rhs._alloc;
    _ptr = rhs._ptr;
    return *this;
}

This is straightforward, just as the noexcept unique_ptr implementation seen above. Likewise, an exception-safe version requires more work but is still possible, thanks to the relocate-and-exchange pattern:

box<T,A> box<T,A>::exchange(box<T,A> other reloc)
requires std::is_nothrow_relocation_constructible_v<A>
{
    box const prev{_ptr, std::reloc_and_uninitialize(std::addressof(_alloc))};
    new (std::addressof(_alloc)) A{reloc other._alloc};
    _ptr = other._ptr;
    return prev;
}

box<T,A>& box<T,A>::operator=(box<T,A> rhs)
{
    exchange(reloc rhs);
    return *this;
}

This implementation has a strong exception safety: should an exception be thrown, the box would still be in a valid state. Indeed, an exception may only be thrown by T’s destructor, and this is only called after the box is set a new valid state (i.e. rhs), when the object returned by exchange is destroyed.

5.5.4. Invocation

T x, y;
x = reloc y;

Every call to the relocation assignment operator follows normal rules.

If the call site detects that an eliding version of the operator is available, then which version of the operator is called is implementation-defined.

The nominal case is to call the non-eliding version. The implementation is allowed to call the eliding version instead, given that the source object is early destructible.

5.6. Overload resolution

The current overload resolution rules are not suitable for relocation by prvalue.

Indeed, consider the following scenario:

void bar(T&&); // same issue with: bar(T const&);
void bar(T);

void foo(T val)
{
    bar(reloc val); /* ambiguous call using today's rules */
}

Hence we propose a change in the overload resolution rules to prefer passing by value for prvalue arguments.

Specifically, we would amend [over.ics.rank]/3.2.3 to read:

  • neither of S1 and S2 bind a reference to an implicit object parameter of a non-static member function declared without a ref-qualifier, and either:

    • S1 binds an lvalue reference to an lvalue, and S2 does not, or:

    • S1 binds an rvalue reference to an xvalue, and S2 does not, or:

    • S1 does not bind a reference, and S2 binds a reference to a prvalue, or:

    • S1 binds an rvalue reference to a prvalue, and S2 binds an lvalue reference [Example:

      int i;
int f1();
int&& f2();
...
int g2(const int&);
int g2(int);
int g2(int&&);
int j2 = g2(i); // calls g2(const int&)
int k2 = g2(f1()); // calls g2(int)
int l2 = g2(f2()); // calls g2(int&&)
...

      - end example]

5.6.1. Comparison against P2665R0

[P2665R0] "Allow calling overload sets containing T, const T&" also proposes to modify the overload resolution rules. It allows overload sets containing both T and T const& to exist, and which overload is selected is implementation-defined. The main motivation is for performance: "small" trivial types, such as built-in integral types, are best passed by value than by reference.

In what we propose, overload sets with T, T const& and T&& can also exist. However, which is picked is (not early destructible objects left aside) specified clearly by the standard (depending on the value category of the parameter) and not implementation-defined.

The reloc operator can be used to turn not-ref-qualified automatic variables into prvalues, which allows the user to force the right overload.

The only situation where the overload being selected is implementation-defined, is when a function parameter passed by value is being relocated. Whether the relocation constructor is considered in the overload resolution is implementation-defined, as it depends on the ABI capabilities. Consider:

void foo(T);
void foo(T&&);

void bar(T value)
{
    foo(reloc value); /* always calls foo(T),
        but how foo's parameter is constructed
        is implementation-defined (reloc, move or copy ctor) */
}

In this example, bar will always call the foo(T) overload, as reloc value is always a prvalue. However, the materialization of this prvalue is implementation-defined, the relocation constructor being potentially evicted.

NOTE: This proposal and P2665R0 can co-exist. Even with the updated overload resolution rules that we propose, compilers may still be allowed to pick the prvalue overload if they analyse it may bring a performance boost, as P2665R0 suggests.

5.7. Structured decomposition

5.7.1. Discussion

auto [x, y] = foo(); sink(reloc y); is ill-formed given the rules we established for reloc. x and y are not complete objects but aliases to some anonymous object which the language creates behind the scene.

As this proposal aims to provide support for relocate-only types, this support would be partial, if not impractical, without allowing some form of relocation from a structured binding.

In our experience, most C++ developers believe that a structured binding is a complete, separate object, and not a name alias to some subobject. As such it would feel unnatural for them if they cannot relocate from a structured binding.

We propose "structured decomposition" as an alternative to structured bindings. Instead of binding the subobjects of the initializer (foo() in the example) to the new identifiers, the initializer is decomposed into the new identifiers. The new identifiers, being individual complete objects, can then be relocated.

5.7.2. Structured decomposition declaration

A structured decomposition declaration is syntactically identical to a structured binding, with the exception that no ref-qualifiers are allowed after the auto type specifier.

T foo();
T const& bar();
T foobar();

// [...]

auto [x, y] = foo(); // matches structured decomposition declaration
auto const [w, z] = bar(); // matches structured decomposition declaration
auto&& [a, b] = foobar(); // structured bindings will be used

The structured decomposition declaration further requires that the type of the expression that is used to initialize it supports any of the structured decomposition protocol. If not, then the declaration is simply a structured bindings declaration and will follow structured bindings rules.

5.7.3. Structured decomposition protocols

As there are three binding protocols for structured bindings, there are likewise three "structured decomposition" protocols. If none of those protocols match, then the declaration is not a structured decomposition declaration, and structured bindings are considered.

The protocols are tested in the following order:

  1. The array protocol ;

  2. The get_all protocol ;

  3. The data members protocol ;

In what follows, let E be the type of the initializer expression (the type of the expression used to initialize the structured decomposition).

  • If E is a glvalue, then let S be the same as E, but deprived of its ref-qualifiers. If one of the three protocols applies, then an anonymous object of type S is constructed from the initializer, using the appropriate constructor. This anonymous object will be considered as the prvalue source object ;

  • Otherwise (E is a prvalue), then let S be the same as E. The initializer expression will be used as source object.

5.7.3.1. array protocol

The array protocol is quite similar to that of structured bindings. For this protocol to apply, all the following conditions must be satisfied:

  • S must be an array-type of known bound ;

  • the number of identifiers must equal the number of array elements ;

If this protocol applies, then the i-th identifier is constructed by relocation, move or copy constructor using the i-th array element as source object.

void foo()
{
    std::string const strs[3] = { /* ... */ };
    // [...]
    auto const [str1, str2, str3] = reloc strs;
    bar(reloc str2);
}
5.7.3.2. get_all protocol

The function get_all(S) is looked-up using ADL-lookup. If there is no match, then this protocol does not apply.

If there is a match, then this function is called (copy-elision will happen, S prvalue will share the same address as get_all parameter slot). The returned type is tested recursively:

  1. If get_all matches for the returned type, then we reapply it again ;

  2. If data members protocol matches for the returned type, then it is applied ;

  3. If no protocol matches for the returned type, then the expression is ill-formed (structured bindings is not tried).

This follows the same recursive logic as operator->(). We recursively call get_all as long as the get_all protocol applies. When the recursion ends, we end up with a type which matches the data member protocol, or else the expression is ill-formed.

NOTE: If there are concerns that get_all(S) may clash with existing functions, then other names may be used, such as __get_all__ or __decompose__.

5.7.3.3. data members protocol

The data members protocol is also similar to that of structured bindings. For this protocol to apply, all the following conditions must be satisfied:

  • every non-static data member of S must be a direct member of S or of the same base class of S ;

  • the number of identifiers must equal the number of non-static data members ;

  • S may not have an anonymous union member ;

  • specific to structured decomposition: for every base class, between S and the base class the data members are found in, its decomposition is well-formed.

If this protocol applies, then the i-th identifier is constructed as if by reloc s.i, s being the decomposed base class holding all the data members and i the i-th identifier.

5.7.3.4. Implementation-defined library support

std::pair, std::tuple, and std::array shall provide their own implementation of get_all. The return type is implementation-defined (may rely on compiler magic).

This allows us to write things like:

void bar(T);
void foo(std::vector<T>& v)
{
    /* This code uses a putative vector::pilfer(const_iterator) (not proposed),
     * which removes a vector element at given iterator, and
     * returns a pair with next valid iterator and relocated vector element. */
    auto [val, it] = v.pilfer(v.begin() + 1); /* calls get_all behind
        the scene. */
    bar(reloc val); /* can call reloc on val as it is not a structured binding */
}

This code works even if T is relocate-only.

5.7.3.5. Possible get_all implementations

Thanks to std::tuple’s get_all we can easily write a get_all implementation for a custom class:

class MyType
{
public:
    MyType();
    MyType(MyType);

    // Possible implementation:
    auto get_all(this MyType self reloc)
    {
        return std::tuple{reloc self._name, self._flag,
            !self._nodes.empty()};
    }

private:
    std::string _name;
    bool _flag;
    std::vector<Node*> _nodes;

};

The implementation relies on a putative new constructor for std::tuple (not proposed) which captures the tuple elements by value category, which allows to relocate objects into a tuple.

Then, in the following snippet:

MyType tp;
auto [name, flag, nodes] = reloc tp;
// equivalent to: auto [name, flag, nodes] = get_all(get_all(reloc tp));

MyType’s get_all returns a tuple. get_all is defined for tuples as well, so it is called again. The second return type won’t have a get_all defined, hence the recursion stops and the data member protocol is used.

6. Proposed library changes

NOTE: Adding support for relocation in the STL is another major change. What we are proposing to add for the moment is the bare minimum to allow library writers to benefit from relocation. Support for relocation in the STL will be done in a separate proposal, depending on the reception of the current proposal.

6.1. Memory header

6.1.1. std::construct_at

We propose to add the following overload to std::construct_at:

template<class T>
constexpr T* construct_at( T* p, T src );

Which would be equivalent to ::new (p) T{reloc src}, except that it may be used in constant expression evaluations.

Note: this overload would be unnecessary if the § 7.6.2 More perfect forwarding direction were to be adopted; instead the existing signature should be altered to use the decltype(Args)... placeholder.

6.1.2. std::reloc_and_uninitialize and std::reloc_and_reclaim

We propose to add the following functions in the std namespace in the memory header to perform relocation through a pointer:

template <class T>
std::remove_cv_t<T> reloc_and_uninitialize(T* src);
template <class T>
std::remove_cv_t<T> reloc_and_reclaim(T* src);

Both functions construct a new object by calling either the virtual slicing function, the relocation constructor, the move constructor or the copy constructor (in that order), using *src as parameter while ignoring its cv-qualifiers, and return it. They also ensure the end-of-life of the source object: if the move or copy constructor is called then the destructor of *src is called afterwards.

reloc_and_uninitialize leaves the memory that was occupied by src in an destructed state (uninitialized memory). Even if it leaves with an exception, then reloc_and_uninitialize is guaranteed to leave the source object in a destructed state.

reloc_and_reclaim reclaims the memory by calling the appropriate deallocation function (class-defined delete or global delete). If reloc_and_reclaim leaves with an exception, then it is guaranteed to leave the source object in a destructed state and to have deallocated its memory.

reloc_and_uninitialize is intended to be used by library authors to enable relocation from a memory address. For instance, extracting a value out of an optional just becomes:

T optional<T>::extract()
{
    _has_value = false;
    return std::reloc_and_uninitialize(_value_addr());
    // _value_addr() being a private function returning the address of the owned value
}

Of course, this function is not intended to be used on local objects. Hopefully its name should prevent misuses.

void foo()
{
    const T val;
    bar(std::reloc_and_uninitialize(&val)); /* BAD, val destructor is called at the
        end of its scope while it is already destructed!*/
}

reloc_and_reclaim is intended to be used by end users and library vendors alike.

unique_ptr<pair<string, box<T>>> makeStuff();

box<T> getBox()
{
    auto stuff = makeStuff();
    auto [str, relocOnly] = std::reloc_and_reclaim(stuff.release());
    return relocOnly;
    // or the short version:
    // return std::reloc_and_reclaim(makeStuff().release()).second;
}

6.1.3. std::relocate

C++26 introduced std::relocate that allows to relocate a range of contiguous objects. This function can be only be used if the object is trivially relocatable or has a non-throwing move constructor.

We propose to amend this function, so that it can also be used if the object has a non-throwing relocation constructor. The function then attempts trivial relocation, then fallbacks to relocation, and then to move construction.

6.2. Type traits header

We propose to introduce the following type traits, which all derive from std::true_type or std::false_type accordingly:

  • std::is_relocation_constructible<T>: same as std::is_constructible<T, T> ;

  • std::is_trivially_relocation_constructible<T>: same as std::is_trivially_constructible<T, T> ;

  • std::is_nothrow_relocation_constructible<T> same as std::is_nothrow_constructible<T, T> ;

  • std::is_relocation_assignable<T>: same as std::is_assignable<T, T> ;

  • std::is_trivially_relocation_assignable<T>: same as std::is_trivially_assignable<T, T> ;

  • std::is_nothrow_relocation_assignable<T>: same as std::is_nothrow_assignable<T, T> ;

  • std::is_decomposable<T>: derives from std::true_type if and only if std::is_class_v<T> is true, and T decomposition is legal ; Derives from std::false_type otherwise ;

The existing trait std::is_trivially_relocatable<T> shall be amended to take into account the updated definition.

For all new type traits, the inline constexpr boolean template variable counterparts are also proposed. For instance we propose to introduce:

template< class T >
inline constexpr bool is_relocation_constructible_v = is_relocation_constructible<T>::value;
// along with the rest

7. Discussions

7.1. Potential ABI changes

As noted above (§ 3.2 Early destructible), some platforms have a caller-destroy ABI where the calling function expects to destroy nontrivial parameters passed by value. This poses a problem for functions that wish to relocate from such parameters, and a potential ABI break.

7.1.1. relocate-only function parameters

In the case study of how reloc should behave with function parameters passed by value, we established the following rule:

Rule: In a temporary materialization, if the reloc operand is a function parameter passed by value, and its type provides an eligible move constructor, then the relocation constructor (if any) may be discarded during overload resolution. Whether the relocation constructor is discarded is implementation-defined.

If the ABI is not already compliant, then this rule will force an ABI change on functions which have parameters passed by value, and whose type declares a relocation constructor but no move constructor.

The good news is as of today, there are no such types, so no existing function should suffer from an ABI break. However, some types may accidently gain a relocation constructor and may trigger an ABI break nonetheless.

In a future library changes proposal to support relocation (separate from this one), we must be careful not to make any existing type relocate-only, especially for that concern. However we will add a relocation constructor on many classes, alongside their existing copy and move constructors. In doing so, some of them may fit the criteria for ABI break, should their copy and move constructors be deleted.

One example is a function with signature: void foo(gsl::non_null<std::unique_ptr<int>>);, supposing unique_ptr gets a relocation constructor. In turn GSL developers will likely add a relocation constructor too. That makes gsl::non_null<std::unique_ptr<int>> relocate-only, while it wasn’t before, and may cause a potential ABI break.

There is zero value of passing a gsl::non_null<std::unique_ptr> by value to a function today, so we doubt anyone would write such a function. However those functions might theoritically exist, and might have an ABI change.

Also, library vendors are encouraged to migrate to an ABI where any function that takes non-trivial parameters by value are responsible for their destruction. Then, the function definitions can make the most out of reloc. This is not required by the proposal.

We believe it’s up to the implementation to choose what they want to do with their ABI:

  • full break, use callee-destroy or equivalent for all non-trivial relocatable types passed by value (for those who don’t care about ABI) ;

  • break with opt-out: a relocation constructor attribute to opt-out of the ABI break on functions where it is passed be value. This solution should also provide propagation mechanisms suitable for composition (these could be standardized at a later date) ;

  • likely no break, but opt-in: an improved [[trivial_abi]] that actually checks that the type is trivially relocatable ;

  • likely no break: use callee-destroy only for relocatable but immovable types ;

  • and those that are callee-destroy already don’t need to do anything!

In all cases the following mitigation and migration techniques could be employed:

  • functions that have an ABI change could be mangled differently. This makes ABI breakage detectable ;

  • for such functions, up to two symbols are emitted, where the old symbol is emitted only if the function does not in actual fact relocate from its parameters, in which case the new symbol is emitted, and its implementation forwards to the old and then destructs its relocatable parameters on exit ;

Last, this potential breakage was discussed on Itanium ABI github, although we didn’t get much feedback.

7.1.2. prvalue assignment operator

As mentioned above, if the class-type is relocatable but immovable, then it may have an impact on existing prvalue-assignment operators (like it does to any function). However this change is purely opt-in. If there is an existing prvalue-assignment operator in a class, then it will prevent the implicit declaration of the relocation constructor, which will in turn prevent from the potential ABI break.

Also, the relocation assignment operator may be aliased. If aliasing occurs, then the ABI does not break as aliasing happens only on a new hidden function.

7.1.3. The virtual slicing function

The introduction of a new virtual function is an ABI break. For this reason, the new virtual slicing function is entirely opt-in. It can only be triggered by an explicit declaration of a relocation constructor. This seems suitable, as a declaring a relocation constructor may already have an impact on existing ABIs.

We identified two areas of concern about virtual slicing functions:

  1. the function is hidden from the developers ;

  2. developers may lose a bit of control over the vtable, as the slicing function is forcibly declared as a side effect of other declarations ;

Both concerns could be addressed by declaring the virtual slicing function differently.

We could allow the relocation constructor to be declared as virtual, and doing so would generate the slicing function. Hence the declaration of the slicing function would no longer be hidden, and changes on the vtable are explicit.

However this solution creates other issues:

  • Although the relocation constructor sort of acts as a destructor, declaring a constructor as virtual is unusual in C++. Besides, overridden relocation constructors in derived classes will have a non-matching first parameter compared to the base class. (If the base class declares virtual B(B reloc), then the derived class declares D(D reloc) override.)

  • If the slicing function is not declared, it may cause unsafe object slicing situations and resource leaks. The situation where we want to support this kind of safe slicing is when dealing with a polymorphic object that can be destructed from a base class pointer. If the language declares the virtual slicing function automatically, then developers cannot get it wrong.

A third solution would be to declare the virtual slicing function as any other function:

struct T
{
    virtual auto operator slice() = default;
};

But this creates other issues:

  • The name of the function needs not to clash with any existing function ;

  • The return value and parameters are implementation-defined, so hardly writable by the developers ;

  • This is an explicit function declaration for which no definition must be supplied ;

  • And the safety point stands: developers may forget to declare it and unsafe object slicing may occur silently.

For all those reasons, and because we believe that safety in the language should come first, we proposed the virtual slicing function to be hidden and automatically declared if the criteria are met.

7.2. Impact of relocation on input parameter passing

C++ provides multple ways to pass parameters to functions, and we expect relocation to have a small impact on the existing practices. We will focus only on the input parameter passing, as output parameters are unaffected by relocation.

There are three ways to pass input parameters to a function:

  • by const reference T const&: the function will not modify this parameter. This is mainly used when the object is not cheap to copy, and hence better pased by constant reference. Ownership transfer is not possible with constant references.

  • by rvalue reference T&&: this is used as an input parameter, while paradoxically the function will likely modify it (leaving it in a moved-from state). This form of parameter passing explicitly indicates an ownership transfer, although the transfer may not happen (see std::map::try_emplace).

  • by value T: this parameter passing is favored against the other two if the cost of the object creation (copy-or-move-constructed) is cheap. This form of parameter passing is less seen in APIs that deal with a generic template type (see std::vector::push_back). This form can be used for ownership transfer, and is the only form that allows relocation.

The "by value" parameter passing will gain more attention as it is the only proposed way to perform relocation. We advise:

  • to pass by value instead of by rvalue reference if the class-type provides a relocation constructor ;

  • to keep passing by rvalue reference if the class-type provides a move constructor and no relocation constructor ;

  • generic APIs should preferably provide the three overloads (by value, by rvalue reference, by const reference). Alternatively, only the "by const reference" and the "by value" overloads could be enough, as the "by value" form allows ownership transfer either with move or relocation.

7.2.1. Compared performance of reloc vs std::move for ownership transfer

This section will compare the performance differences between std::move and reloc, across the different input parameter passing policies. As std::move cannot be used with parameters passed by constant references, this form will be left out.

Let’s consider a common scenario. We have an automatic variable src, and we want to transfer its resources to some other system. This is achieved by a series of function calls, where each function will forward the source object to the next, until it reaches the target system. The object is always forwarded either by std::move across the whole chain, either by reloc. Each function may take its input parameter either by value, or by rvalue reference. Imagine that each function is defined in different translation units. We will measure the performance in terms of object creation.

std::move (by rvalue ref) relocation (by value) 
void foo()
{
    T src = getT();
    sink_1(std::move(src));
}
void sink_1(T&& src)
{
    sink_2(std::move(src));
}
void sink_2(T&& src)
{
    sink_3(std::move(src));
}
// ...
void sink_N(T&& src);

A single object is created, in foo.

 
void foo()
{
    T const src = getT();
    sink_1(reloc src);
}
void sink_1(T src)
{
    sink_2(reloc src);
}
void sink_2(T src)
{
    sink_3(reloc src);
}
// ...
void sink_N(T src);

Depending on the implementation (if relocation elision can happen all the way), we have a single object creation in foo, or N object creations (one in each function body).

std::move (by value) relocation (by rvalue ref) 
void foo()
{
    T src = getT();
    sink_1(std::move(src));
}
void sink_1(T src)
{
    sink_2(std::move(src));
}
void sink_2(T src)
{
    sink_3(std::move(src));
}
// ...
void sink_N(T src);

N objects are created, one in each function body.

 
void foo()
{
    T const src = getT();
    sink_1(reloc src);
}
void sink_1(T&& src)
{
    sink_2(reloc src);
}
void sink_2(T&& src)
{
    sink_3(reloc src);
}
// ...
void sink_N(T&& src);

This design may seem a bit peculiar, but may happen during an aggressive search and replace in a code base to replace std::move calls to reloc.

In foo’s body, the reloc src expression promotes src to a prvalue. As src is early destructible, the temporary materialization is elided and the prvalue is directly converted to an xvalue. After the full expression evaluation, foo will implicitly invoke src’s destructor. Successive reloc expressions in the sink_i functions will operate from an xvalue src, performing xvalue forwarding as if by std::move. We have a single object creation.

You can see that in the worst case, reloc is not worse than std::move if all functions are "by value". It has the same performance as std::move if all functions are "by rvalue reference" (but then no relocation can be done), or if all functions are "by value" and the implementation can elide all the relocations. This is why we say that reloc and std::move provide overall a similar performance, one performing better than the other in specific situations.

7.2.2. Achieving 0-copy transfer with a cooperative ABI

Let f be a function which takes an object of non-trivial type T as value parameter: void f(T);. To call f, the Itanium ABI chooses to pass the parameter by address. The following happens in the caller:

  1. a temporary object is created, initialized from the expression passed in the matching parameter slot of the function call expression.

  2. f is called, passing the address of the temporary object instead of the whole object bytefield.

  3. when the function returns (normally or through an exception), the temporary object is destroyed.

Now, let us say that T has migrated to relocation semantics: it has a relocation constructor, but no move constructor. This alone makes any object of type T early destructible, and eligible to relocation elision. Hence, with the Itanium ABI and relocation elision, the expression f(reloc obj) translates into a call to f, merely forwarding the address of obj. No temporaries are created.

For instance, in the following snippet:

void vector<T>::push_back(T x) // putative std::vector push_back
{
  ensures_space();
  new (_end++) T{reloc x};
}

void bar(T x)
{
  get_vector().push_back(reloc x);
}

void foo(T x)
{
  if (test()) bar(reloc x);
}

// in some function:
T x;
foo(reloc x);

Translates into this pseudo-C++ code:

void vector<T>::push_back(T* x)
{
  ensures_space();
  memcpy(_end++, x, sizeof(T)); // given that relocation is trivial
}

void bar(T* x)
{
  get_vector().push_back(x);
}

void foo(T* x)
{
  if (test()) bar(x);
  else x->~T();
}

// in some function:
T x;
foo(&x);
// x destructor is not called

This allows the object to be created once, and forwarded by address until it is relocated inside a vector. No useless copies are created. Yet no new value categories were introduced, all happened with value-semantics, and the code is safe as static analysis ensures the object is not reused after reloc. This can be achieved only because of relocation elision and the fact that value parameters are passed by address in Itanium ABI.

This proposal does not mandate this implementation, we only highlight that such an implementation is possible. Also, if this proposal is approved, it will create an opportunity for other ABIs to migrate to something similar, should they wish to benefit from this optimization.

7.2.3. About clang’s trivial_abi

Consider the following void foo(T obj);. foo takes obj by value. In Itanium ABI, it translate differently in terms of ABI depending whether T is trivial or not:

  • If trivial, then obj is passed by value as expected, meaning that a copy of obj is constructed in foo’s parameter slot memory space. clang’s trivial_abi states that foo body then owns obj which makes obj early destructible.

  • Otherwise, as pointed out above, a copy of obj is constructed as a temporary object, and the address of that temporary is passed to foo. Then obj in foo body is not early destructible.

clang’s trivial_abi is a non-standard class attribute. It forces the class-type to be considered as trivial for value parameter passing.

Is this attribute helpful for relocation? Yes and no. On one hand, this makes the object early destructible which enables relocation. But on the other hand, the object is passed down to foo (not its address), which prevents relocation elision of obj in foo body.

The cooperative ABI discussed above is arguably better (pass by address, and give ownership). This enables both relocation and its elision, ... but at the cost of having to dereference the obj pointer when the object is accessed.

Note that this paper does not enforce one parameter passing or the other, we only mandate obj to be early destructible if T has a relocation constructor and no move constructor (so the second call convention is amended for those types).

7.3. std::exchange and std::swap

We have long hesitated to propose new overloads to std::exchange and std::swap, which would use relocation semantics instead of move, further improving support for relocate-only types.

Such an std::exchange overload would be:

template <class T>
requires std::is_nothrow_relocation_constructible_v<T> &&
std::is_final_v<T>
constexpr T exchange(T& obj, T new_value) noexcept
{
    T const old{std::reloc_and_uninitialize(std::addressof(obj))};
    std::construct_at(std::addressof(obj), reloc new_value);
    return old;
}

This function works by destroying obj and relocating new_value on top of it. You will have noticed the bunch of requirements:

  • The relocation constructor must not throw. Should an exception be emitted by a relocation constructor, then exchange would leave obj in an uninitialized state, opening the door for future disasters.

  • To prevent from reconstructing over obj with a different type, T must be final. For instance this is prohibited:

    class D : public B { std::string _str; };

D obj;
B old = std::exchange(static_cast<B&>(obj), B{});
// obj destructor will attempt to destroy `_str` which is uninitialized memory.

The same set of requirements would apply to std::swap. We feel that the requirements are too strong to ever be practical. In particular, no STL classes use the final specifier, and frameworks in general are as unlikely to use it, which greatly diminishes the usefulness of such overloads.

Relocation-based and byteswap-based versions of std::exchange and std::swap may be implemented and used by library vendors, to grant a performance boost and improved support for relocate-only types. Those overloads can be used safely in controled environments (for instance in container implementations, where there is no surprise in the dynamic type of the stored object).

7.3.1. Relocating data members

std::exchange and std::swap with relocation semantics are not proposed, to the detriment of relocate-only type support. This is why we recommend every relocate-only type to provide an exchange member function, as an alternative to std::exchange but with relocation semantics. Such a function enables to relocate a data member (or any non-complete object) similarly to what is done today with std::move.

struct A
{
    std::box<T> take_box() { return box_.exchange(); }
    // [...]
};

std::pair<int, std::box<T>> p = getPair();
foo(p.second.exchange());

Such an exchange function can be implemented without resorting to destroy and reconstruct, as it can take advantage of the private access to lift off some blocking class invariants.

NOTE: the exchange member function is to be used when the data member is to be reused. If it belongs to an object that is about to be destroyed, then object decomposition is the preferred approach as the cost to reconstruct a valid state is avoided.

struct A
{
    std::box<T> take_box(this A self reloc) { return self.box_; }
    // [...]
};

std::pair<int, std::box<T>> p reloc = getPair();
foo(reloc p.second);

7.4. Object decomposition alternatives

In R3, object decomposition took the form of "decomposing functions". An object could only be decomposed through a member function:

class T {
    // [..]
    auto extract(this T reloc) { return _obj; }
private:
    reloc_only_t _obj;
};

This had drawbacks:

  • As objects could only be decomposed through member functions, it implied that:

    • Decomposition had to happen through a dedicated function ;

    • Decomposition had to happen within the class-type ;

  • It was hard to decompose more than one object at a given time ;

  • This used a weird syntax to access base classes: reloc B, with B being a base class.

We wanted decomposition to be more convenient to use, as it is an intrinsically close concept to relocation. It took several attempts to reach what we propose in this paper.

7.4.1. The dot-reloc operator

We studied for a while a putative dot-reloc operator: p.reloc first. The first time the expression was evaluated, the object used as the left operand would become decomposed, and the subobject used as the right operand would be relocated. Once decomposed, the source object could no longer be used normally. We restricted the expressions where a decomposed object would be allowed, down to:

  • data member access ;

  • cast to base class ;

  • base member function call ;

For instance:

pair<string, string> p = getPair();
if (test()) {
    foo(p.reloc first); // p is now decomposed, p.first is relocated
    bar(p.second); // ok
}
foobar(p); // ko: p may be decomposed

And it could even work with pointer to data-members, given that they were constant-evaluated:

template <auto DataMember>
string Get(pair<string, string> p)
{
    return p.*reloc DataMember;
}

This approach proved quite convenient to use. However it suffured from much added complexity:

  1. the code could be hard to follow because objects would be decomposed only when the first .reloc operator was evaluated ;

  2. the static information of the object (for instance, whether some expressions involving the object are valid), which are supposed to remain unchanged during the program ... would change when the first .reloc operator was evaluated ;

  3. relocating a base class still has the unusual syntax: src.reloc BaseClass ;

  4. lots of new rules to learn on how to handle a decomposed object ;

  5. would complicate code parsing, as the validity of an id-expression designing an object would depend on the surrounding expressions, should this object be decomposed or potentially decomposed.

This motivated us to make a take a dractically different approach.

7.4.2. The namespace approach

Most of the issues raised above come from the fact that a decomposed object could still be used as an object. This made code parsing complicated, especially considering that an object could become decomposed from within a code branch, so it could not be known at compile-time whether the object was decomposed.

For this reason, we made two changes:

  • an object cannot be decomposed on the fly, it needs to be declared as decomposed, and ;

  • a decomposed object is no longer an object, and can only be used as a proxy to designate its direct data member and base classes.

The main idea was that the decomposed object would be exploded into a dedicated special namespace, named after the object name. For instance:

pair<string, string> p reloc = getPair();
// p becomes a namespace containing all its direct subobjects
if (test()) {
    foo(reloc p::first);
    bar(p::second);
}
foobar(p); // ko: p is not a value

struct D : public B {};
D d reloc = D{};
foo(reloc d::B); // relocates base class

This approach addressed all the points raised above, while still being convenient to use. There were two aspects where it compared unfavorably to dot-reloc, is that for one it could not relocate a subobject from a pointer to data member, or from a base class whose name is passed as a template type parameter:

template <string T::*_str>
string GetStr(T obj reloc)
{
    return obj::*_str; // invalid expression
}
template <class B>
B GetBase(T obj reloc)
{
    return obj::B; // invalid expression
}

Second, the namespace syntax was too unusual for C++, so a third approach, taking the best of the two was picked.

7.4.3. The proposed approach

We believe the proposed approach addresses all the points raised above, while still being convenient to use. This approach is close to the namespace approach, except that a dot operator is used instead of the namespace resolution operator (which feels nore natural to access data members). And this syntax makes it easier to support relocation of a data member through a constant-evaluated pointer-to-member.

Code parsing is not made more complex, as the object must be declared as decomposed, and the decomposed object does not yield a value. There is still the unsual obj.Base syntax, (which is made possible as obj is decomposed and is not a value) but we consider this to be a minor issue.

7.6. Future directions

We removed some of the changes we initilialy had in mind, to keep for future extensions. This proposal aims to be the bare minimum to bring support for relocate-only types.

7.6.1. STL support for relocation and relocate-only types

The current proposal focuses mainly on the core language changes. It seems a bit early for us to start discussing new STL APIs while there is not yet any agreement on the core language changes.

However, when and if a consensus is reached, we do plan to add relocate-only type support for the STL, and at least a relocate-only pointer type (std::box). The API changes we plan are among:

  • add a relocation constructor and relocation assignment operator to most STL classes. Types with no move constructor or polymorphic types will be left out to avoid introducing ABI breaks.

  • In containers, add the ability to insert and extract (= remove and return) elements with relocation semantics.

  • In utility types (optional, variant, expected, pair, tuple, etc...) add the ability to emplace an object with relocation semantics. More perfect forwarding will likely be a prerequisite.

7.6.2. More perfect forwarding

Currently, "perfect forwarding" is built on top of universal references, requiring an understanding of reference-collapsing and the use of std::forward. The present proposal improves on this by incidentally replacing std::forward with reloc, but at the same time the situation is worsened by making relocate-only types viable; such types cannot be relocated when passed by universal reference.

Before After 
template <class... Args>
void fwd(Args&&... args)
{
    do_stuff(std::forward<Args>(args)...);
}

template <class... Args>
void fwd(Args&&... args)
{
    do_stuff(reloc args...);
}

Future 
template <class... Args>
void fwd(decltype(Args)... args)
{
    do_stuff(reloc args...);
}
// OR equivalently
void fwd(decltype(auto)... args)
{
    do_stuff(reloc args...);
}

We suggest a new way to deduce template type parameters, by allowing decltype(T) in the function parameters (only if T is a function template type parameter). With this addition, it would become possible to deduce each parameter to value, lvalue reference or rvalue reference according to whether the argument is of value category prvalue, lvalue or xvalue, and forward by relocation.

7.6.3. discarded reloc expression

Initilialy, discarded reloc expressions such as reloc obj; would simply translate to a call to the destructor of obj, while ensuring that the destructor won’t be called again at the end of its scope.

However this is hardly possible at the moment because of all the different ABIs that exist. If obj is not early destructible, then the function cannot elide the destructor call of obj that will happen on the caller-side.

We wanted the well-formedness of the code above all else (i.e. reloc obj; could not be well-formed on some implementations and not in others).

Hence, the best we can do if obj is not early destructible, is to move-construct a temporary, and destruct it right after, which will trigger the desired side-effects of the destructor (e.g. release a lock if obj is a unique_lock). The destructor of obj will still be called when the function returns, but will likely do nothing as the object will be in a moved-from state.

A future proposal could make reloc obj; to just call the destructor, regardless of whether obj is early destructible and of its constructors, solving those ABI issues.

7.7. Will it make C++ easier?

This proposal introduces a new keyword, and a bunch of new concepts (relocation constructor, decomposition), which are additional things to teach. However we have hopes this proposal will improve the language on many areas and eradicate some gotchas:

  • support for relocation-only types, which allow for better class design with stronger class invariants ;

  • reloc aims to fix the "moved-from state" understanding problem, and the used-after-move errors ;

  • relocation fixes the const pessimization with move constructor ;

  • reloc creates more opportunities to declare constant variables, improving on code readability and performance.
